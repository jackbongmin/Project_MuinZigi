## 핵심 개념
- **측정 장치가 개선보다 먼저**: 개선한 뒤에는 개선 전 상태를 다시 만들기 어려움. 그래서 측정 로그부터 만듦
- **한 줄 = 단계 실행 한 번**: 판단은 502 뒤에 다시 불러 이어서 할 수 있어서, 영상 하나에 한 줄이 아니라 실행할 때마다 한 줄을 추가함
- **`finally`**: 예외가 나도 실행됨. 예외는 잡지 않고 그대로 밖으로 나감 (502 응답은 그대로)
- **트랜잭션과 기록**: 추출은 `@Transactional`이라 실패하면 측정 로그도 롤백됨. 판단은 `save()`마다 바로 저장해서 실패해도 남음
- **`@Enumerated(EnumType.STRING)`**: enum을 순서 번호가 아니라 이름으로 저장함. 값을 끼워 넣어도 기존 기록의 뜻이 안 바뀜

## 코드 흐름
1. `POST /api/videos/{id}/frames` → `FrameService.extract()`: 시작 시각 → 측정 로그 생성(설정값은 `FrameSelector.settings()`) → 추출·고르기·저장 → `recordFrames(전체, 고른 수)` → `finish(true, 시간)` → 저장
2. `POST /api/videos/{id}/judgments` → `JudgmentService.judge()`: 판단할 프레임 확인 → 측정 로그 생성 → `try` 안에서 프레임마다 `judgeOne()`
   - 성공: `addJevCalls(시도 수)`, `addJudgedFrame(토큰)`
   - 실패: `addJevCalls(시도 수)` 후 502 예외
   - `finally`: `finish(성공 여부, 시간)` → 저장
3. `GET /api/videos/{id}/measurements` → `MeasurementService.findAll()`: 영상이 없으면 404, 있으면 `id` 순서로 응답

## 궁금해서 물어본 것
### 테스트는 어떤 영상으로 하나
- 기본 테스트(`gradlew test`)는 N·P 영상을 쓰지 않음. 테스트할 때 FFmpeg로 6초짜리 영상(3초 검은 화면 → 3초 흰 화면, `TestVideos.blackThenWhite`)을 그 자리에서 만들어 씀
  - 정답이 확실함 (6장 뽑아 5장 고름), 영상이 저장소에 없어도 돎 (`.gitignore`), 빠름
  - Jev는 가짜(`@MockitoBean`)라서 "우리 코드가 맞게 처리하나"만 확인함
- N·P 영상은 두 곳에서 씀
  - `gradlew jevTest`: 실제 Jev 판단 정확도를 잼 (`JevFrameLiveTest`, `JevShelfLiveTest` 등). 비용이 들어서 기본 테스트에서 뺌
  - 가이드 끝의 실제 서버 확인: P1을 curl로 올려 전체 흐름, 시간, 토큰을 잼

### 의존성 주입(DI)은 어디서, 왜 하나
- **일을 하는 객체**(Controller, Service, Repository, `JevClient` 같은 `@Component`)는 생성자로 **주입받음.** 서버가 뜰 때 Spring이 하나씩 만들어 필요한 생성자에 넣어 줌
  - 방향은 Controller → Service → Repository·도구 한쪽으로만 감
- **데이터를 담는 객체**(엔티티, DTO, `Map`)는 요청마다 내용이 달라서 `new`로 직접 만듦
- 직접 `new` 하지 않는 이유
  1. 테스트에서 가짜로 바꿔 끼울 수 있음. `JevClient`를 주입받아서 테스트에서 `@MockitoBean`으로 바꿔 Jev 비용 없이 테스트함
  2. 만드는 방법을 한 곳(`JevConfig`)만 알게 됨
  3. 하나를 여러 곳에서 같이 씀 (`MeasurementLogRepository`를 `FrameService`, `JudgmentService`가 같이 받음)
- 생성자가 하나면 `@Autowired` 없이도 Spring이 넣어 줌. 테스트 클래스는 JUnit이 만들어서 필드에 `@Autowired`를 씀
