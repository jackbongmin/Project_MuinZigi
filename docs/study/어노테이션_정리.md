# 어노테이션 정리

- 처음 작성: 2026-10-30 (가이드 04까지)
- 우리 프로젝트 코드(`backend/src`)에 실제로 나온 어노테이션만 모음. 가이드에 새 어노테이션이 나오면 여기에 추가함
- "처음 나온 곳"은 그 어노테이션을 처음 쓴 단계·가이드임. 그 가이드의 개념 설명에 더 자세한 내용이 있음

## 0. 어노테이션이란
- `@`로 시작하는 **표시(라벨)**임. 어노테이션 자체는 아무 일도 하지 않음
- **누군가 이 표시를 읽고 일을 해 줌.** 누가 읽느냐로 나누면 덜 헷갈림

| 누가 읽나 | 언제 | 예 |
|---|---|---|
| **Spring** | 서버가 뜰 때 클래스를 훑어보고 객체를 만들고 연결함 | `@Service`, `@RestController`, `@Value`, `@Transactional` |
| **JPA(Hibernate)** | 엔티티를 DB 테이블·칸과 짝지을 때 | `@Entity`, `@Column`, `@ManyToOne` |
| **Jackson** | 객체 ↔ JSON 변환할 때 | `@JsonProperty`, `@JsonIgnoreProperties` |
| **JUnit** | 테스트를 실행할 때 | `@Test`, `@BeforeEach`, `@TempDir` |
| **Spring 테스트** | 테스트용 Spring을 띄울 때 | `@SpringBootTest`, `@MockitoBean` |
| **자바 컴파일러** | 컴파일할 때 | `@Override` |

- 괄호 안 값은 설정임. `@Column(nullable = false)`는 "이 칸은 비면 안 됨"이라는 설정을 붙인 것임

## 1. Spring: 객체를 만들고 연결하기 (빈 등록과 주입)
Spring은 서버가 뜰 때 아래 표시가 붙은 클래스를 찾아 **객체를 하나씩 만들어 보관함**(이 객체를 **빈(bean)**이라고 부름). 그리고 생성자에 필요한 빈을 넣어 줌(**주입**).

| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@SpringBootApplication` | 시작 클래스 | 이 패키지 아래를 훑어서 빈을 찾고, 설정을 자동으로 맞추고, 서버를 띄움 | `MujinjigiApplication` | 0단계 |
| `@Component` | 클래스 | "이 클래스로 빈을 만들어라". 가장 기본 | `JevClient`, `FrameExtractor`, `FrameSelector`, `VideoFileStorage` | 0단계 |
| `@Service` | 클래스 | `@Component`와 기능은 같음. "업무 로직 담당"이라는 **이름표**를 더 붙인 것 | `VideoService`, `FrameService`, `JudgmentService` | 가이드 01 |
| `@RestController` | 클래스 | 빈 등록 + "이 클래스는 HTTP 요청을 받고, 반환값을 JSON으로 돌려줌" | `VideoController`, `JudgmentController` | 가이드 01 |
| `@Configuration` | 클래스 | "이 클래스는 설정 클래스임. 안의 `@Bean` 메서드를 실행해라" | `JevConfig` | 가이드 04 |
| `@Bean` | `@Configuration` 안의 메서드 | 이 메서드가 **돌려준 객체**를 빈으로 보관함. 내가 만든 클래스가 아니라 직접 설정해서 만들어야 하는 객체(`RestClient`)에 씀 | `JevConfig.jevRestClient()` | 가이드 04 |
| `@Value("${키}")` | 생성자 인자 | `application.properties`(와 `.env`)의 값을 넣어 줌 | `@Value("${jev.model}") String model` | 0단계 |
| `@Autowired` | 필드 | 이 필드에 빈을 넣어 줌. **우리는 테스트에서만 씀**. 기능 코드는 생성자로 받음(생성자가 하나면 Spring이 알아서 넣어 줌) | 테스트의 `MockMvc mockMvc`, `JevCallLogRepository` | 가이드 01 |

**헷갈리는 점**
- `@Component` / `@Service` / `@RestController`: 셋 다 빈을 만듦. `@Service`는 이름표만 다르고, `@RestController`는 HTTP 처리 기능이 더 있음
- `@Component` vs `@Bean`
  - `@Component`: **클래스에** 붙임. Spring이 `new`를 대신 해 줌
  - `@Bean`: **메서드에** 붙임. 내가 직접 만들어서(주소, 시간 제한 설정) 돌려준 객체를 Spring이 보관함
- 생성자 주입 vs `@Autowired`: 기능 코드는 `private final` 필드 + 생성자로 받음. 테스트 클래스는 생성자를 Spring이 부르지 않아서 필드에 `@Autowired`를 씀
- Repository 인터페이스(`VideoRepository` 등)에는 어노테이션이 없음. `JpaRepository`를 상속하면 Spring Data가 알아서 빈으로 만듦

## 2. Spring: HTTP 요청 받기 (컨트롤러)
| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@RequestMapping("/주소")` | 컨트롤러 클래스 | 이 클래스의 모든 메서드 앞에 붙는 **공통 주소** | `@RequestMapping("/api/videos/{videoId}/judgments")` | 가이드 01 |
| `@PostMapping` | 메서드 | POST 요청을 이 메서드가 받음 | `JudgmentController.judge()` | 가이드 01 |
| `@GetMapping("/{id}")` | 메서드 | GET 요청을 이 메서드가 받음. 괄호 안은 공통 주소 뒤에 붙는 주소 | `VideoController.find()` | 가이드 01 |
| `@PathVariable` | 메서드 인자 | 주소 안의 `{videoId}` 자리 값을 꺼내 줌 | `@PathVariable Long videoId` | 가이드 01 |
| `@RequestParam("file")` | 메서드 인자 | 요청의 파라미터·폼 필드 값을 꺼내 줌. 업로드 파일도 이걸로 받음 | `@RequestParam("file") MultipartFile file` | 가이드 01 |

**헷갈리는 점**
- `@PathVariable` vs `@RequestParam`: `/api/videos/3` 처럼 **주소 안**에 있으면 `@PathVariable`, `?page=2`나 폼 필드처럼 **주소 밖**에 있으면 `@RequestParam`

## 3. Spring: 트랜잭션
| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@Transactional` | 서비스 메서드 | 메서드 안의 DB 작업을 **한 묶음**으로 처리함. 중간에 예외가 나면 전부 되돌림 | `FrameService.extract()` | 가이드 01 |
| `@Transactional(readOnly = true)` | 조회 메서드 | 읽기만 한다고 알림. 변경 감지를 건너뛰어 조금 가벼워짐 | `VideoService.find()`, `FrameService.findAll()` | 가이드 01 |
| `@Transactional` | **테스트 클래스** | 테스트마다 트랜잭션을 열고, **끝나면 무조건 되돌림**. 테스트 데이터가 DB에 남지 않음 | `VideoControllerTest`, `JudgmentControllerTest` | 가이드 01 |

**헷갈리는 점**
- 같은 어노테이션인데 **서비스에서는 "실패하면 되돌림"**, **테스트에서는 "항상 되돌림"**으로 동작이 다름
- `JudgmentService.judge()`에는 일부러 안 붙임. Jev 호출(장당 약 0.3초, 재시도면 몇 초)을 하는 동안 DB 연결을 잡고 있지 않으려고 함 (가이드 03 1-5)
- 같은 클래스 안에서 `this.다른메서드()`로 부르면 `@Transactional`이 적용되지 않음. Spring이 객체 바깥에 덧씌운 껍데기(프록시)를 거쳐야 동작하기 때문임

## 4. JPA: 엔티티와 테이블 짝짓기
| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@Entity` | 클래스 | 이 클래스는 DB 테이블 한 줄과 짝지어짐 | `Video`, `VideoFrame`, `FrameJudgment`, `JevCallLog` | 가이드 01 |
| `@Table(name = "videos")` | 클래스 | 짝지을 테이블 이름. 없으면 클래스 이름을 씀 | `@Table(name = "jev_call_logs")` | 가이드 01 |
| `@Id` | 필드 | 이 필드가 기본 키(PK) | `private Long id;` | 가이드 01 |
| `@GeneratedValue(strategy = IDENTITY)` | `@Id` 필드 | 키 값을 DB가 자동으로 1, 2, 3… 매김 | 모든 엔티티의 `id` | 가이드 01 |
| `@Column` | 필드 | 칸 설정. `nullable = false`(비면 안 됨), `columnDefinition = "text"`(칸 타입 직접 지정) | `@Column(nullable = false, columnDefinition = "text") String requestBody` | 가이드 01 |
| `@ManyToOne(fetch = LAZY, optional = false)` | 필드 | 여러 개가 하나에 속함(N:1). `LAZY`는 실제로 꺼낼 때 읽음 | `VideoFrame.video`, `FrameJudgment.frame`, `JevCallLog.frame` | 가이드 02 |
| `@JoinColumn(name = "video_id")` | `@ManyToOne` 필드 | 연결에 쓰는 외래 키 칸 이름 | `@JoinColumn(name = "frame_id")` | 가이드 02 |
| `@JdbcTypeCode(SqlTypes.JSON)` | 필드 | 자바 `Map`을 JSON으로 바꿔 저장함(Hibernate 기능). `columnDefinition = "jsonb"`와 같이 씀 | `FrameJudgment.answers` | 가이드 03 |
| `@Query("select ...")` | Repository 메서드 | 메서드 이름 규칙 대신 JPQL을 직접 씀. fetch join처럼 이름으로 표현 못 할 때 | `FrameJudgmentRepository.findAllWithFrame()` | 가이드 03 |

**헷갈리는 점**
- `@Entity`가 없으면 `@Table`·`@Column`도 의미가 없음. `@Entity`가 "JPA가 관리하는 클래스"라는 시작 표시임
- `@Column(nullable = false)`는 **DB 칸**에 NOT NULL을 거는 것임. 요청 값 검사(`@NotNull` 같은 검증)와는 다름. 우리는 아직 검증 어노테이션을 쓰지 않음
- `@ManyToOne`에 `LAZY`를 붙이면 N+1이 생길 수 있음. 같이 읽어야 하는 조회에서는 `@Query`로 fetch join함 (트러블슈팅 2026-10-30 N+1)

## 5. Jackson: JSON 변환
| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@JsonIgnoreProperties(ignoreUnknown = true)` | record·클래스 | JSON에 모르는 필드가 있어도 오류 없이 무시함. 외부 API 응답에서 필요한 칸만 받을 때 | `JevResponse` | 0단계 |
| `@JsonProperty("input_tokens")` | 필드·record 인자 | JSON 이름과 자바 이름이 다를 때 짝지어 줌 (`input_tokens` ↔ `inputTokens`) | `JevResponse.Usage` | 0단계 |

- 우리 API 응답 DTO(`VideoResponse` 등)에는 붙이지 않음. 자바 이름 그대로 JSON 이름이 되어도 괜찮아서임

## 7. 테스트: JUnit
| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@Test` | 메서드 | 이 메서드가 테스트 하나임 | 모든 테스트 메서드 | 0단계 |
| `@BeforeEach` | 메서드 | **각 테스트 전에 매번** 실행됨. 가짜 응답 정하기, 객체 새로 만들기 | `JevClientTest.setUp()` | 가이드 03 |
| `@TempDir` | 필드 | 테스트용 임시 폴더를 만들어 넣어 주고, 끝나면 지움 | `Path tempDir` (테스트 영상 만들 때) | 가이드 02 |
| `@Tag("jev")` | 테스트 클래스 | 테스트에 이름표를 붙임. `build.gradle`에서 이 이름표로 기본 테스트에서 빼거나(`excludeTags`) 따로 돌림(`jevTest`) | `JevClientLiveTest` 등 실제 Jev 호출 테스트 | 0단계 |

## 8. 테스트: Spring
| 어노테이션 | 붙는 곳 | 하는 일 | 우리 프로젝트 예 | 처음 나온 곳 |
|---|---|---|---|---|
| `@SpringBootTest` | 테스트 클래스 | 테스트용으로 **Spring 전체**(빈, DB 연결)를 띄움. `properties = "..."`로 설정을 바꿀 수 있고, `classes = {...}`로 일부 빈만 띄울 수도 있음 | `VideoControllerTest`, `@SpringBootTest(classes = {JevConfig.class, JevClient.class})` | 0단계 |
| `@AutoConfigureMockMvc` | 테스트 클래스 | `MockMvc`를 빈으로 만들어 줌. 서버를 진짜로 띄우지 않고 HTTP 요청을 흉내 냄 | `JudgmentControllerTest` | 가이드 01 |
| `@MockitoBean` | 테스트 필드 | Spring이 가진 진짜 빈을 **가짜(mock)로 바꿔치기**함 | `@MockitoBean JevClient jevClient` | 가이드 03 |

**헷갈리는 점**
- `@SpringBootTest`가 없는 테스트(`FrameSelectorTest`, `JevClientTest`)는 `new`로 객체를 직접 만듦. Spring을 띄우지 않아서 훨씬 빠름. 빈 주입이나 DB가 필요 없으면 이쪽이 나음
- `@MockitoBean`은 `@SpringBootTest`와 같이 쓸 때만 의미가 있음. Spring이 없으면 바꿔치기할 빈도 없음
- mock이 무엇이고 언제 쓰는지는 `03일차_문서보완_Jev프레임판단.md`의 "mock 정리"에 있음

## 9. 지금 코드에서 한눈에 보기
`JudgmentService` 한 클래스에 붙은 표시만 봐도 역할이 나뉨:
```java
@Service                                   // Spring: 빈으로 만듦 (업무 로직)
public class JudgmentService {
    public JudgmentService(VideoRepository videoRepository, ..., JevClient jevClient) { ... }
    //                     ↑ 생성자 하나 → Spring이 필요한 빈을 넣어 줌 (어노테이션 없음)

    public List<FrameJudgmentResponse> judge(Long videoId) { ... }
    // @Transactional 없음: Jev 호출 동안 DB 연결을 잡지 않으려고 일부러 뺌
}
```
