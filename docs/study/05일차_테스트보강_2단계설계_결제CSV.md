## 핵심 개념
- **커버리지는 "어디를 안 봤나"를 찾는 도구**: % 목표 대신 빨간 줄을 하나씩 보고 실제로 생길 수 있는 경우인지 판단함
- **테스트는 기능에 영향을 주지 않음**: `src/test`와 `testImplementation` 라이브러리는 서버 실행·배포 jar에 들어가지 않음. 검사 대상은 진짜이고 바깥(HTTP 요청, Jev 서버)만 가짜로 바꿈
- **저장 = DB 표에 써 넣는 것, 계속 남김**: CSV 파일은 버리고 내용을 DB로 옮김. 판정·재분석·웹 화면에서 계속 읽음. "형식 검사"(오늘)와 "결제 vs 영상 대조"(나중 판정 로직)는 다른 단계임
- **전부 저장하거나 하나도 저장하지 않거나**: 검사를 저장보다 먼저 끝내고 저장은 한 트랜잭션. 일부만 저장되면 결제한 손님이 미결제로 잡힘
- **파서를 서비스에서 떼어 냄**: Spring 없이 빠른 단위 테스트가 되고, 나중에 다른 키오스크 양식이 와도 파서 쪽만 바꾸면 됨
- **테스트 통과 ≠ 실제 응답**: MockMvc는 서버 안쪽에서 이유를 꺼내 봐서, 실제 응답에서 이유가 빠진 것을 못 잡았음

## 코드 흐름 (결제 CSV 업로드)
1. `PaymentController.upload()` → `PaymentService.upload(file)`
2. 빈 파일·확장자 검사 → `PaymentCsvParser.parse(글자)`: BOM 제거 → 줄 나누기 → 헤더 확인 → 줄마다 칸 수·형식·금액 검사 → `List<PaymentCsvRow>`
3. 틀리면 `IllegalArgumentException("N번째 줄: ...")` → 서비스가 400 `ResponseStatusException`으로 바꿈 → Problem Details가 `detail`에 이유를 넣어 응답
4. 다 맞으면 결제 합계 계산 → `PaymentUpload` 저장 → `PaymentRecord` 여러 줄 `saveAll` (한 트랜잭션) → 201 + `Location`

## AI 결과를 의심하고 확인한 것
- **2단계 계획에 개수 문제가 빠져 있었음**: "10개 집고 8개만 결제하면 잡을 수 있나?"라고 물음 → Claude Code가 결정 001 설계(칸마다 예/아니오)를 다시 보고, 서로 다른 상품은 잡지만 같은 상품 여러 개는 못 잡는다고 인정함 → 결과: 설계의 구멍이 맞았음. 2단계에 개수 실험과 결정 기록을 넣음
- **범인 식별용 장면이 계획에 없었음**: 의심 장면의 대표 캡처가 "넣는 장면" 기준이라 얼굴이 안 나올 수 있었음 → 얼굴 캡처와 증거 묶음을 2단계에 넣고, 얼굴 인식은 하지 않기로 선을 그음
- **가이드 07이 우리 양식 CSV만 읽음**: "양식이 완전히 다른 키오스크면 사장이 일일이 고쳐야 하나?"라고 물음 → Claude Code가 실제로 다른 양식은 400으로 거절된다고 확인함 → 결과: 맞았음. 3단계에 양식별 변환기와 칸 매핑 설정을 넣음

## 스스로 답해볼 질문
1. 커버리지 % 목표를 두지 않고 빈 곳을 하나씩 판단한 이유는 무엇인가. 커버리지 100%면 버그가 없다고 할 수 있는가 (면접 질문)
2. 테스트 코드는 왜 `src/main`이 아니라 `src/test`에 두는가. 테스트는 실제 기능에 영향을 주는가
3. 금액을 `double`이 아니라 `long`(원 단위)으로 저장한 이유는 무엇인가 (면접 질문)
4. CSV에 틀린 줄이 하나라도 있으면 전체를 저장하지 않는 이유는 무엇인가. 일부만 저장되면 이 서비스에서 어떤 문제가 생기는가
5. MockMvc 테스트는 통과했는데 실제 서버 응답에는 오류 이유가 없었던 이유는 무엇인가
6. 같은 상품 10개 중 8개만 결제한 경우를 지금 설계로 못 잡는 이유는 무엇인가. 어떻게 확인하고 결정할 계획인가
