# 가이드 08 · 방문 나누기

> **한 줄 요약**: 1단계에서 쌓은 **프레임 판단(`frame_judgments`)의 `person` 확률**을 시간순으로 읽어, 사람이 이어서 보이는 구간을 **방문 하나(`visits`)**로 묶어 저장하고 조회 API로 꺼내 보는 기능 구현임. 사람이 5초보다 오래 안 보이면 방문이 끝남

## 목표
- 2단계 판정의 **단위인 방문**을 만듦 (결정 006). 다음 항목인 진열대 전후 비교, 결제 대조, 의심 장면이 모두 방문 하나를 기준으로 움직임
- 나누는 규칙은 Spring·DB 없이 동작하는 클래스(`VisitSplitter`)에 두고, 경계값(판정 기준 0.5, 끊김 허용 5초)을 단위 테스트로 확인함
- 기준값은 설정 파일로 뺌. 3단계 정확도 측정에서 바꿔 가며 잴 수 있게 함
- Jev를 다시 부르지 않음. 이미 저장된 판단 결과만 읽음 (비용 0)

## 완료 기준
- `.\gradlew.bat clean test` 통과 (새 테스트 10개 포함, 전체 53개)
- 실제 서버에서 P1 판단이 있는 영상으로 방문을 나누면 **방문 1개, 11초 ~ 19초, 9장**이 나옴

## 바뀌는 API
| 요청 | 응답 |
|---|---|
| `POST /api/videos/{videoId}/visits` | `201` + 방문 목록 (시각 순). 다시 부르면 이전 방문을 지우고 새로 나눔. 없는 영상 `404`, 판단 전이면 `409` |
| `GET /api/videos/{videoId}/visits` | `200` + 방문 목록 (시각 순). 없는 영상 `404` |

## 1. 개념 먼저

### 1-1. 방문이 왜 필요한가
- 지금까지는 **프레임 한 장마다** 판단이 있을 뿐, "손님 한 명"이라는 단위가 없음
- 그런데 판정은 손님 단위로 해야 함
  - 진열대 전후 비교: 손님이 **들어오기 전**과 **나간 뒤** 진열대를 비교함 → 언제 들어오고 나갔는지 알아야 함
  - 결제 대조: 그 손님이 **머문 시간 안에** 결제가 있었나 → 시작·끝 시각이 필요함
  - 의심 장면: 점주에게 "이 손님"을 보여 줌 (방문 하나당 의심 장면 하나)
- 그래서 **방문 = 사람이 처음 보인 시각 ~ 마지막으로 보인 시각**으로 정함 (handoff 14장 "방문")

### 1-2. 나누는 규칙 두 가지 (결정 006)
1. **사람이 보였나**: 프레임의 `person` 확률이 **0.5 이상**이면 보인 것으로 봄 (판정 기준, handoff 14장)
2. **방문이 끝났나**: 사람이 마지막으로 보인 시각과 다음에 보인 시각의 **차이가 5초보다 크면** 앞 방문을 닫고 새 방문을 시작함

P1 실제 판단 결과로 보면 이렇게 됨:
```
시각(초)  0    1    2    3   (4~7 프레임 없음)   8    9    10   11   12 ... 19
person   0.06 0.07 0.07 0.07                    0.07 0.08 0.30 0.98 0.98 ... 0.97
보였나    ✗    ✗    ✗    ✗                      ✗    ✗    ✗    ✓    ✓   ...  ✓
                                                             └──── 방문 1: 11 ~ 19초, 9장 ────┘
```
- 10초의 0.30은 손이 화면 끝에 살짝 걸친 정도라 기준(0.5) 아래임 → 방문에 안 들어감

끊김 허용 5초가 어떻게 동작하는지 (프레임은 1초에 1장):
```
보인 시각:  10 · · · · 15          → 차이 5초 (11~14초 4장 안 보임)  → 같은 방문
보인 시각:  10 · · · · · 16        → 차이 6초 (11~15초 5장 안 보임)  → 다른 방문
```
- "5초 이상 안 보이면 끝"을 1초 간격 프레임으로 옮기면 "차이가 5초보다 크면 끝"이 됨
- 끊김을 허용하는 이유: 손님이 진열대 앞에서 몸을 숙이거나 기둥에 잠깐 가려지면 몇 장 동안 `person`이 낮게 나올 수 있음. 허용이 없으면 한 손님이 방문 여러 개로 쪼개짐

### 1-3. 프레임이 없는 시간은 "안 보인 것"으로 봄
- 가이드 02에서 **활동 구간**의 프레임만 남겼음. 조용한 시간(P1의 4~7초)은 프레임 자체가 없음
- 공백을 "안 보인 프레임 수"로 세면, 프레임이 없는 시간은 세지 못함. 3초에 보이고 다음 프레임이 20초라면 사이에 안 보인 프레임이 0장이라 방문이 이어져 버림
- 그래서 **시각 차이**로 잼. 3초 → 20초는 차이 17초라 자연스럽게 다른 방문이 됨
- 결정 006의 "활동 구간 밖(프레임이 없는 시간)도 안 보인 것으로 봄"이 이 한 줄(`frame.timeSec() - last > gapSeconds`)로 해결됨

### 1-4. 계산(`VisitSplitter`)과 저장(`VisitService`)을 나눔
| 클래스 | 하는 일 | Spring·DB |
|---|---|---|
| `VisitSplitter` | 시각·확률 목록 → 방문 구간 목록 | 계산에는 필요 없음 (설정값만 `@Value`로 받음) |
| `VisitService` | 판단 결과 읽기 → `VisitSplitter` 호출 → 저장 | 필요함 |
- 가이드 07의 `PaymentCsvParser`와 같은 방식임. 규칙이 가장 자주 틀리는 곳이라 **Spring 없이 `new VisitSplitter(0.5, 5)`로 바로 테스트**함
- 가이드 02의 `FrameSelector`도 `@Component` + `@Value`지만 테스트에서는 `new`로 만들었음. 같은 모양임
- `VisitSplitter`가 엔티티(`FrameJudgment`) 대신 작은 record를 받고 돌려줌
  - 받는 것 `PersonFrame(시각, person 확률)`: `FrameJudgment`를 만들려면 `Video` → `VideoFrame` → `FrameJudgment` 순서로 다 만들어야 해서 테스트가 길어짐. 나누기에 필요한 건 두 값뿐임
  - 돌려주는 것 `VisitRange(시작, 끝, 장 수)`: 엔티티(`Visit`)는 영상(`Video`)에 속해야 만들 수 있는데, 계산 단계에서는 영상을 몰라도 됨
- 2단계의 **판정 로직**(시각 맞추기, 대조, 의심도)도 이렇게 "순수 계산 클래스 + 서비스"로 만들 예정임 (handoff 5장, 줄·분기 100%)

### 1-5. 다시 나누면 지우고 새로 저장함
- 설정(0.5, 5초)을 바꾸면 같은 영상을 다시 나눠야 함. 판단 결과는 그대로 있으니 Jev는 다시 부르지 않음
- `POST`를 다시 부르면 **이전 방문을 지우고 새 결과를 저장**함. 둘을 `@Transactional` 한 묶음으로 처리해서, 저장 중 오류가 나면 지운 것도 되돌림 (방문이 하나도 없는 상태로 남지 않음)
- `deleteByVideoId`: 가이드 02의 `findByVideoId...`처럼 **메서드 이름으로 만드는 삭제 쿼리**임. 이름 규칙 삭제는 트랜잭션 안에서만 동작함 (밖에서 부르면 오류)
- 판단(가이드 03)은 "이미 한 프레임은 건너뜀"이었는데 방문은 "지우고 새로" 하는 이유: 판단은 Jev 비용이 들어서 다시 하면 안 되고, 방문 나누기는 DB 안에서 계산만 하니 매번 새로 해도 비용이 없음

### 1-6. 경계값 테스트
기준값이 있는 규칙은 **기준 바로 위·아래**를 꼭 확인함. 부등호 하나(`<` ↔ `<=`)를 틀리면 경계에서만 결과가 달라지기 때문임

| 경계 | 아래 | 위 | 테스트 |
|---|---|---|---|
| 판정 기준 0.5 | 0.49 → 안 보임 | 0.5 → 보임 | `확률이_판정_기준과_같으면_사람으로_본다` |
| 끊김 허용 5초 | 차이 5초 → 같은 방문 | 차이 6초 → 다른 방문 | `공백이_5초면_같은_방문이다`, `공백이_5초를_넘으면_다른_방문이다` |

### 3-2. `service/VisitRange.java`

```java
package com.mujinjigi.domain.analysis.service;

/**
 * 2단계 · 08 (방문 나누기)
 * 방문 나누기의 결과 한 줄. "손님이 몇 초부터 몇 초까지 있었나"를 담음 (DB에 저장하기 전)

 * @param endSec     사람이 마지막으로 보인 시각(초)
 * @param frameCount 방문 안에서 사람이 보인 프레임 수
 */
public record VisitRange(double startSec, double endSec, int frameCount) {
}
```

### 3-3. `service/VisitSplitter.java`

```java
package com.mujinjigi.domain.analysis.service;

import java.util.ArrayList;
import java.util.List;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

/**
 * 2단계 · 08 (방문 나누기)
 * 프레임별 "사람 있음" 확률을 시간순으로 보고, 손님 한 명이 머문 구간(방문)으로 잘라 주는 클래스
 * 예: 11~19초에 사람이 보이고 300~340초에 또 보이면 → 방문 2개 [11~19초], [300~340초]
 * 사람이 5초 넘게 안 보이면 거기서 자름 (설정 app.visit.gap-seconds, 결정 006). 계산에 Spring·DB가 필요 없음
 */
@Component
public class VisitSplitter {

    private final double personThreshold;
    private final double gapSeconds;

    public VisitSplitter(@Value("${app.visit.person-threshold}") double personThreshold,
                         @Value("${app.visit.gap-seconds}") double gapSeconds) {
        this.personThreshold = personThreshold;
        this.gapSeconds = gapSeconds;
    }

    /**
     * @param frames 판단을 마친 프레임 (시각 순서)
     * @return 방문 목록 (시각 순서). 사람이 한 번도 안 보이면 빈 목록
     */
    public List<VisitRange> split(List<PersonFrame> frames) {
        List<VisitRange> visits = new ArrayList<>();
        double start = 0;
        double last = 0;
        int count = 0;   // 지금 이어 붙이는 방문의 프레임 수. 0이면 진행 중인 방문이 없음

        for (PersonFrame frame : frames) {
            if (frame.personProbability() < personThreshold) {
                continue;   // 사람이 안 보이는 프레임은 건너뜀. 공백은 아래에서 시각 차이로 잼
            }
            // 마지막으로 보인 시각과의 차이가 gapSeconds보다 크면 앞 방문을 닫고 새 방문을 시작함
            // 프레임이 없는 시간(활동 구간 밖)도 시각 차이에 들어가므로 "안 보인 것"으로 계산됨
            if (count > 0 && frame.timeSec() - last > gapSeconds) {
                visits.add(new VisitRange(start, last, count));
                count = 0;
            }
            if (count == 0) {
                start = frame.timeSec();
            }
            last = frame.timeSec();
            count++;
        }
        // 마지막 방문은 반복문 안에서 닫히지 않으므로 여기서 넣음
        if (count > 0) {
            visits.add(new VisitRange(start, last, count));
        }
        return visits;
    }
}
```
- 변수 세 개로 "지금 만드는 중인 방문"을 들고 다님: `start`(시작), `last`(마지막으로 보인 시각), `count`(장 수)
- 사람이 보인 프레임마다 두 가지를 물음
  1. 진행 중인 방문이 있고, 마지막으로 보인 지 5초가 넘었나 → 그 방문을 닫아 목록에 넣고 `count = 0`
  2. 진행 중인 방문이 없나(`count == 0`) → 이 프레임에서 새 방문 시작
- 반복이 끝났을 때 진행 중인 방문은 아직 목록에 안 들어가 있음 → 마지막 `if`에서 넣음. **이 줄을 빼먹으면 마지막 방문이 사라짐** (테스트가 잡아 줌)
- 판정 기준은 `< personThreshold`면 건너뜀 → 0.5는 "보임". 끊김은 `> gapSeconds`면 닫음 → 차이 5초는 "이어짐" (1-6)

### 3-4. 테스트: `service/VisitSplitterTest.java` (`src/test` 아래)

```java
package com.mujinjigi.domain.analysis.service;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.List;

import org.junit.jupiter.api.Test;

/**
 * 2단계 · 08 (방문 나누기)
 * VisitSplitter가 방문을 제대로 자르는지 확인하는 테스트. Spring·DB 없이 바로 실행됨
 * 기준값 바로 위·아래(확률 0.49 / 0.5, 공백 5초 / 6초)에서 결과가 맞는지 봄
 */
class VisitSplitterTest {

    // 판정 기준 0.5, 공백 5초 (application.properties와 같은 값)
    private final VisitSplitter splitter = new VisitSplitter(0.5, 5);

    @Test
    void 사람이_안_보이면_방문이_없다() {
        List<PersonFrame> frames = List.of(
                new PersonFrame(1, 0.1),
                new PersonFrame(2, 0.49),
                new PersonFrame(3, 0.0));

        assertThat(splitter.split(frames)).isEmpty();
    }

    @Test
    void 확률이_판정_기준과_같으면_사람으로_본다() {
        List<PersonFrame> frames = List.of(
                new PersonFrame(1, 0.49),
                new PersonFrame(2, 0.5));

        assertThat(splitter.split(frames)).containsExactly(new VisitRange(2, 2, 1));
    }

    @Test
    void 사람이_이어서_보이면_방문_하나로_묶는다() {
        List<PersonFrame> frames = List.of(
                new PersonFrame(1, 0.9),
                new PersonFrame(2, 0.8),
                new PersonFrame(3, 0.95),
                new PersonFrame(4, 0.7));

        assertThat(splitter.split(frames)).containsExactly(new VisitRange(1, 4, 4));
    }

    @Test
    void 공백이_5초면_같은_방문이다() {
        // 10초 다음에 15초에 다시 보임 → 차이 5초 (11~14초 4장 안 보임) → 이어짐
        List<PersonFrame> frames = List.of(
                new PersonFrame(10, 0.9),
                new PersonFrame(11, 0.1),
                new PersonFrame(12, 0.1),
                new PersonFrame(13, 0.1),
                new PersonFrame(14, 0.1),
                new PersonFrame(15, 0.9));

        assertThat(splitter.split(frames)).containsExactly(new VisitRange(10, 15, 2));
    }

    @Test
    void 공백이_5초를_넘으면_다른_방문이다() {
        // 10초 다음에 16초에 다시 보임 → 차이 6초 (11~15초 5장 안 보임) → 나뉨
        List<PersonFrame> frames = List.of(
                new PersonFrame(9, 0.9),
                new PersonFrame(10, 0.9),
                new PersonFrame(11, 0.1),
                new PersonFrame(12, 0.1),
                new PersonFrame(13, 0.1),
                new PersonFrame(14, 0.1),
                new PersonFrame(15, 0.1),
                new PersonFrame(16, 0.9));

        assertThat(splitter.split(frames)).containsExactly(
                new VisitRange(9, 10, 2),
                new VisitRange(16, 16, 1));
    }

    @Test
    void 프레임이_없는_시간도_안_보인_것으로_본다() {
        // 3초 다음 프레임이 20초 (사이는 활동 구간 밖이라 프레임이 없음) → 나뉨
        List<PersonFrame> frames = List.of(
                new PersonFrame(2, 0.9),
                new PersonFrame(3, 0.9),
                new PersonFrame(20, 0.9),
                new PersonFrame(21, 0.9));

        assertThat(splitter.split(frames)).containsExactly(
                new VisitRange(2, 3, 2),
                new VisitRange(20, 21, 2));
    }
}
```

```java
package com.mujinjigi.domain.analysis.entity;

import com.mujinjigi.domain.video.entity.Video;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

/**
 * 2단계 · 08 (방문 나누기)
 * 손님 한 명이 매장에 머문 구간을 DB(visits 테이블)에 저장하는 엔티티
 * 예: 영상 69번의 11초~19초에 손님이 있었음 → video 69, startSec 11, endSec 19, frameCount 9
 * 다음 단계의 진열대 비교·결제 대조·의심 장면이 이 구간을 기준으로 함 (결정 006)
 */
@Entity
@Table(name = "visits")
public class Visit {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "video_id")
    private Video video;

    // 사람이 처음 보인 시각(초)
    @Column(nullable = false)
    private double startSec;

    // 사람이 마지막으로 보인 시각(초)
    @Column(nullable = false)
    private double endSec;

    // 방문 안에서 사람이 보인 프레임 수
    @Column(nullable = false)
    private int frameCount;

    protected Visit() {
    }

    public Visit(Video video, double startSec, double endSec, int frameCount) {
        this.video = video;
        this.startSec = startSec;
        this.endSec = endSec;
        this.frameCount = frameCount;
    }

    public Long getId() {
        return id;
    }

    public Video getVideo() {
        return video;
    }

    public double getStartSec() {
        return startSec;
    }

    public double getEndSec() {
        return endSec;
    }

    public int getFrameCount() {
        return frameCount;
    }
}
```
- `VideoFrame`(가이드 02)과 같은 모양임. 영상 하나에 방문 여러 개 → `@ManyToOne`
- 프레임 id 목록은 저장하지 않음. 방문 안의 프레임이 필요하면 `startSec ~ endSec` 시각으로 찾으면 됨 (진열대 전후 비교에서 씀)
- 패키지를 `analysis`에 둔 이유: 방문은 판단 결과를 가공한 분석 결과임. `suspicion`(의심 장면)은 방문을 판정한 **결과**를 담는 곳이라 다음 단계에서 씀

### 3-8. `service/VisitService.java`

```java
package com.mujinjigi.domain.analysis.service;

import java.util.List;

import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.server.ResponseStatusException;

import com.mujinjigi.domain.analysis.dto.VisitResponse;
import com.mujinjigi.domain.analysis.entity.FrameJudgment;
import com.mujinjigi.domain.analysis.entity.Visit;
import com.mujinjigi.domain.analysis.jev.FrameQuestions;
import com.mujinjigi.domain.analysis.repository.FrameJudgmentRepository;
import com.mujinjigi.domain.analysis.repository.VisitRepository;
import com.mujinjigi.domain.video.entity.Video;
import com.mujinjigi.domain.video.repository.VideoRepository;

/**
 * 2단계 · 08 (방문 나누기)
 * 영상의 판단 결과를 DB에서 꺼내 VisitSplitter로 방문을 자르고, 결과를 visits 테이블에 저장하는 클래스
 * 흐름: 판단 결과 읽기 → (시각, 사람 확률)만 뽑기 → 방문 자르기 → 예전 방문 지우고 새로 저장
 */
@Service
public class VisitService {

    private final VideoRepository videoRepository;
    private final FrameJudgmentRepository frameJudgmentRepository;
    private final VisitRepository visitRepository;
    private final VisitSplitter visitSplitter;

    public VisitService(VideoRepository videoRepository,
                        FrameJudgmentRepository frameJudgmentRepository,
                        VisitRepository visitRepository,
                        VisitSplitter visitSplitter) {
        this.videoRepository = videoRepository;
        this.frameJudgmentRepository = frameJudgmentRepository;
        this.visitRepository = visitRepository;
        this.visitSplitter = visitSplitter;
    }

    // 이전 방문 지우기와 새 방문 저장을 한 트랜잭션으로 묶음. 저장 중 오류가 나면 이전 방문이 그대로 남음
    @Transactional
    public List<VisitResponse> split(Long videoId) {
        Video video = findVideo(videoId);
        List<FrameJudgment> judgments = frameJudgmentRepository.findAllWithFrame(videoId, FrameQuestions.VERSION);
        if (judgments.isEmpty()) {
            throw new ResponseStatusException(HttpStatus.CONFLICT, "프레임 판단을 먼저 해야 함: " + videoId);
        }

        // 판단 결과에서 시각과 person 확률만 꺼냄. 판단 결과는 이미 시각 순서로 읽힘
        List<PersonFrame> frames = judgments.stream()
                .map(judgment -> new PersonFrame(
                        judgment.getFrame().getTimeSec(),
                        judgment.getAnswers().getOrDefault("person", 0.0)))
                .toList();

        // 설정을 바꿔 다시 나눌 수 있게, 이전 결과를 지우고 새로 저장함
        visitRepository.deleteByVideoId(videoId);
        List<Visit> visits = visitSplitter.split(frames).stream()
                .map(range -> new Visit(video, range.startSec(), range.endSec(), range.frameCount()))
                .toList();
        visitRepository.saveAll(visits);

        return visits.stream().map(VisitResponse::from).toList();
    }

    @Transactional(readOnly = true)
    public List<VisitResponse> findAll(Long videoId) {
        findVideo(videoId);
        return visitRepository.findByVideoIdOrderByStartSecAsc(videoId).stream()
                .map(VisitResponse::from)
                .toList();
    }

    private Video findVideo(Long videoId) {
        return videoRepository.findById(videoId)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "영상이 없음: " + videoId));
    }
}
```
- `findAllWithFrame`: 가이드 03에서 만든 fetch join 조회를 그대로 씀. 프레임 시각(`getFrame().getTimeSec()`)을 읽어도 프레임을 한 번 더 조회하지 않음 (N+1 없음)
- `getOrDefault("person", 0.0)`: 혹시 `person` 답이 없는 판단이 있으면 "안 보임"으로 처리함. 키 이름 `"person"`은 `FrameQuestions`의 질문 이름과 같아야 함
- 판단이 하나도 없으면 409: "영상은 있는데 순서상 아직 못 함"이라는 뜻임. 가이드 03에서 프레임 추출 전에 판단하면 409를 준 것과 같은 규칙임
- `saveAll` 뒤에 `visits`의 `id`가 채워져 있음. `IDENTITY` 방식은 저장하는 순간 DB가 번호를 매겨 돌려주기 때문임 → 응답에 `id`가 들어감

```java
package com.mujinjigi.domain.analysis.controller;

import java.net.URI;
import java.util.List;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import com.mujinjigi.domain.analysis.dto.VisitResponse;
import com.mujinjigi.domain.analysis.service.VisitService;

/**
 * 2단계 · 08 (방문 나누기)
 * 방문 API 요청을 받는 클래스
 * POST /api/videos/{id}/visits → 방문을 잘라 저장하고 목록을 돌려줌 / GET → 저장된 방문 목록
 */
@RestController
@RequestMapping("/api/videos/{videoId}/visits")
public class VisitController {

    private final VisitService visitService;

    public VisitController(VisitService visitService) {
        this.visitService = visitService;
    }

    // POST → 201 + 방문 목록. 다시 부르면 이전 방문을 지우고 새로 나눔. 없는 영상 404, 판단 전이면 409
    @PostMapping
    public ResponseEntity<List<VisitResponse>> split(@PathVariable Long videoId) {
        List<VisitResponse> visits = visitService.split(videoId);
        return ResponseEntity.created(URI.create("/api/videos/" + videoId + "/visits")).body(visits);
    }

    // GET → 200 + 시각 순 방문 목록
    @GetMapping
    public List<VisitResponse> findAll(@PathVariable Long videoId) {
        return visitService.findAll(videoId);
    }
}
```

## 5. 알려진 한계 (면접에서 물어볼 만한 부분)
1. **손님 둘이 연달아 들어오면 방문 하나로 합쳐짐**: 앞 손님이 나가고 5초 안에 다음 손님이 들어오면 구분하지 못함. 합쳐지면 A가 가져간 콜라를 B의 콜라 결제가 가릴 수 있음. 2단계에서 "두 명 이상 보이나" 질문을 더해, 결제가 도난을 가릴 수 있는 경우만 "여러 명" 표시와 함께 낮음으로 남김 (결정 007). 사람마다 번호를 매기는 추적은 하지 않음
2. **5초보다 오래 가려지면 한 손님이 쪼개짐**: 진열대 뒤에서 오래 몸을 숙이면 방문 두 개가 됨. 끊김 허용 시간은 첫 값이라 3단계 정답표로 재며 조정함
3. **한 장짜리 방문이 생길 수 있음**: `person`을 한 장만 잘못 높게 받아도 방문 하나가 됨. 의심도는 행동·진열대 근거가 없으면 0이라 의심 장면까지는 안 가지만, 방문 수 집계는 틀어짐. 필요하면 "최소 장 수" 설정을 더함
4. **판단이 중간에 실패한 영상**: 판단(가이드 04)이 502로 멈추면 남은 프레임은 판단이 없어서 "안 보인 것"으로 처리됨. 판단을 이어서 끝낸 뒤 다시 나누면 됨 (다시 나누기가 그래서 있음)
5. **나눌 때 쓴 설정값을 저장하지 않음**: 결과만 보면 0.5·5초로 나눈 것인지 알 수 없음. 3단계에서 설정을 바꿔 가며 측정할 때 측정 로그에 남기는 것을 같이 함
6. **판정 로직이 아직 방문을 쓰지 않음**: 이번 가이드는 방문을 만들고 저장하는 데까지임. 진열대 전후 비교(다음 항목)에서 방문 시작 전·끝 뒤 프레임을 고를 때 처음 씀
