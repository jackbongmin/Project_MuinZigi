## 1. 개념 먼저

### 1-1. 커버리지는 "어디를 안 봤나"를 찾는 도구임
- 커버리지 %는 **테스트가 실행한 줄의 비율**임. 실행했다고 결과를 확인했다는 뜻은 아님 (1일차 Location 버그는 테스트가 다 통과하는 상태에서 남아 있었음)
- 그래서 handoff 8장은 전체 % 목표를 두지 않음. 대신 **빨간 줄(한 번도 안 돈 줄)을 하나씩 보고 "이 경우를 확인해야 하나"를 판단**함
- 이번에 고른 기준: **사용자가 실제로 겪을 수 있는 경우**인가
  | 빈 곳 | 실제로 생기나 | 이번에 |
  |---|---|---|
  | 영상 조회 `GET /api/videos/{id}` 정상 응답 | 웹·앱이 매번 부름 | **채움** |
  | 확장자 없는 파일 이름 (`P1`) | 사용자가 확장자 없는 파일을 올릴 수 있음 | **채움** |
  | FFmpeg 실패 (종료 코드 ≠ 0) | 확장자만 mp4인 깨진 파일 | **채움** |
  | Jev 연결이 끝까지 안 됨 | Jev 서버 장애, 네트워크 끊김 | **채움** |
  | API 키 없음 | `.env`에 키를 안 넣고 서버를 켬 | **채움** |
  | `catch (IOException)` (디스크 오류) | 생기지만 테스트로 만들기 어려움 | 둠 |
  | `catch (InterruptedException)` (스레드 중단) | 서버 종료 중에만 생김 | 둠 |
  | `MujinjigiApplication.main()` | 테스트는 `main`을 거치지 않고 Spring을 띄움 | 둠 |

### 1-2. 줄 커버리지와 분기 커버리지
- **줄(line)**: 그 줄이 한 번이라도 실행됐나
- **분기(branch)**: `if`의 참·거짓, `||`·`&&`의 각 조건이 **양쪽 결과를 다** 내 봤나
- `||`는 왼쪽이 참이면 오른쪽을 아예 보지 않음 (단락 평가). 그래서 조건 2개짜리 `||`는 분기가 4개로 셈
  ```java
  if (filename == null || !filename.contains(".")) {   // 분기 4개
  ```
  | 테스트 | `filename == null` | `!filename.contains(".")` |
  |---|---|---|
  | `P1.mp4` (기존) | 거짓 | 거짓 |
  | `P1` (이번에 추가) | 거짓 | **참** |
  | 이름이 `null` | **참** | (안 봄) |
- 이름이 `null`인 경우는 테스트로 만들 수 없음. `MockMultipartFile`은 이름에 `null`을 넣으면 빈 문자열 `""`로 바꿔 저장함. 실제 요청에서도 Spring이 파일 이름이 없으면 `""`를 줌. 그래서 `VideoService`는 분기 7 / 8에서 멈춤 (5장 한계 1)
- 보고서에서 **노란 줄**이 "분기 중 일부만 실행됨"이고, 줄 왼쪽 마름모에 마우스를 올리면 `1 of 4 branches missed.`처럼 몇 개를 놓쳤는지 보임

### 1-3. 실패하는 경우를 테스트로 만드는 세 가지 방법
정상 흐름은 정상 입력만 넣으면 되지만, 실패 경우는 **실패를 일부러 만들어야** 함. 이번 가이드에 세 가지가 다 나옴

| 방법 | 어디서 | 어떻게 |
|---|---|---|
| 잘못된 입력을 넣음 | FFmpeg 실패 | 확장자만 `.mp4`이고 내용은 글자인 파일을 만들어 진짜 FFmpeg에 넣음 |
| 가짜 서버가 실패를 흉내 냄 | Jev 연결 실패 | `MockRestServiceServer`가 응답 대신 `ConnectException`을 던지게 함 (가이드 04의 시간 초과와 같은 방법) |
| 설정값을 비움 | API 키 없음 | `JevClient`를 직접 만들면서 키 자리에 `" "`(공백)을 넣음 |

- 실패 테스트는 "예외가 났다"에서 멈추지 않고 **어떤 예외인지, 메시지와 기록이 맞는지**까지 확인함. 예외만 확인하면 엉뚱한 곳에서 난 예외로도 통과할 수 있음
  ```java
  IllegalStateException e = assertThrows(IllegalStateException.class, () -> ...);
  assertThat(e.getMessage()).contains("FFmpeg 실패");   // 종료 코드 검사에서 난 예외가 맞는지
  ```

### 1-4. "요청을 보내지 않았다"를 확인하는 법
- API 키 테스트에서 확인할 것은 **Jev에 요청이 아예 가지 않았다**는 것임 (키 없이 보내면 403만 와서 원인을 알기 어려움. 가이드 03에서 막아 둔 이유)
- `MockRestServiceServer`는 `expect(...)`로 **등록하지 않은 요청이 오면 그 자리에서 실패**함. 그래서 아무것도 등록하지 않은 가짜 서버를 붙이고 `verify()`까지 통과하면 "요청 0번"이 확인됨
- 기존 `setUp()`의 `server`·`jevClient`는 키가 `"test-key"`로 만들어져 있어서, 이 테스트 안에서 키가 빈 `JevClient`를 따로 만듦

### 1-5. 앞 요청의 응답을 다음 요청에 쓰기
- 영상 조회 테스트는 먼저 올려야 조회할 id가 생김. id를 `1`처럼 정해 두면 DB 시퀀스 값에 따라 깨짐
- 업로드 응답의 `Location` 헤더(`/api/videos/7`)를 꺼내 그대로 `get(location)`에 넣음. 1일차에 고친 Location 헤더가 **실제로 조회 가능한 주소인지**도 함께 확인됨
  ```java
  String location = mockMvc.perform(multipart("/api/videos").file(file))
          .andReturn().getResponse().getHeader("Location");
  ```
- `andReturn()`: 기대값 확인(`andExpect`) 대신 응답 자체를 돌려받음

## 3. 코드 작성
기존 테스트 클래스 3개의 전체 코드임. **코드 안에 표시한 부분만 새로 치면 됨.** 표시 주석(`★ 추가`)은 위치를 알려 주는 용도라 치지 않음

| 표시 | 뜻 |
|---|---|
| `// ===== ★ 추가 (가이드 06) 시작 =====` ~ `끝 =====` | 이 사이의 메서드를 새로 침 |
| 줄 끝 `// ★ 추가 (가이드 06)` | 이 한 줄(import)을 새로 침 |
| 줄 끝 `← ★ 추가 (가이드 06)` | 클래스 주석에 이 줄을 새로 침 |
| `★ 삭제` | 지울 줄. **이번 가이드에는 지울 줄이 없음** |

표시가 없는 줄은 이미 파일에 있는 코드이므로 건드리지 않음. 각 추가 부분의 설명은 파일 아래 "새로 친 부분"에 있음

| 파일 | 추가 테스트 |
|---|---|
| `video/controller/VideoControllerTest.java` | 확장자 없는 파일 400, 올린 영상 조회 200 |
| `video/service/FrameExtractorTest.java` | 영상이 아닌 파일이면 FFmpeg 실패 예외 |
| `analysis/jev/JevClientTest.java` | 연결이 끝까지 안 되면 예외, API 키가 비면 요청 안 보냄 |

```java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.multipart;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

/**

@Transactional
public class VideoControllerTest {
```

```java
import static org.junit.jupiter.api.Assertions.assertThrows;  // ★ 추가 (가이드 06)

class FrameExtractorTest {

    void 일초에_한장씩_뽑고_장면이_바뀐_시각의_점수가_높다() throws Exception {

        assertThat(tempDir.resolve("frames").resolve(frames.get(0).fileName())).exists();

    void 영상이_아닌_파일이면_FFmpeg_실패_예외를_던진다() throws Exception {
        // 확장자만 mp4이고 내용은 글자인 파일 → FFmpeg가 읽지 못해 종료 코드 0이 아닌 값으로 끝남
        Path notVideo = Files.writeString(tempDir.resolve("fake.mp4"), "not a video");
        FrameExtractor extractor = new FrameExtractor("ffmpeg");

        IllegalStateException e = assertThrows(IllegalStateException.class,
                () -> extractor.extract(notVideo, tempDir.resolve("frames")));
```

**새로 친 부분**
- `import static org.junit.jupiter.api.Assertions.assertThrows;` 추가
- `Files.writeString(경로, 내용)`: 글자를 파일로 쓰고 그 경로를 돌려줌. `@TempDir` 폴더 안이라 테스트가 끝나면 지워짐
- FFmpeg는 이 파일을 영상으로 읽지 못해 종료 코드 1로 끝남 → `runFfmpeg()`의 `exitCode != 0` 줄이 처음 실행됨
- 메시지에는 FFmpeg가 남긴 오류 출력도 붙음 (`redirectErrorStream(true)`로 모아 읽은 것). 실패 원인을 로그에서 바로 볼 수 있게 한 장치가 실제로 동작하는지 확인하는 셈임

```java
import static org.springframework.test.web.client.response.MockRestResponseCreators.withException;
import static org.springframework.test.web.client.response.MockRestResponseCreators.withStatus;
import static org.springframework.test.web.client.response.MockRestResponseCreators.withSuccess;
import static org.springframework.test.web.client.response.MockRestResponseCreators.withTooManyRequests;

import java.io.InputStream;
import java.net.ConnectException;  // ★ 추가 (가이드 06)
import java.net.SocketTimeoutException;
import java.util.Base64;
import java.util.List;
import java.util.Map;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.MediaType;
import org.springframework.mock.http.client.MockClientHttpResponse;
import org.springframework.test.web.client.MockRestServiceServer;
import org.springframework.web.client.RestClient;

/**
 * 1단계 · 04 (Jev 재시도와 원문 로그)
 * 1단계 · 06 (연결 실패·API 키 없음 테스트 추가)   ← ★ 추가 (가이드 06)
 * JevClient 테스트. 진짜 Jev 대신 가짜 서버(MockRestServiceServer)가 정해 둔 응답을 돌려줌
 * Spring 없이 객체를 직접 만들어서 빠르게 확인함
 */
class JevClientTest {

    private static final String URL = "https://jev.test/v1/systemone";
    private static final Map<String, String> QUESTIONS = Map.of("person", "Is there a person in the image `photo`?");
    private static final String OK_BODY = """
            {"model": "jev-1.14.0",
             "answers": {"person": {"type": "noul", "noul": 0.9}},
             "usage": {"input_tokens": 2803, "output_tokens": 0}}
            """;
    private static final byte[] IMAGE = {1, 2, 3};

    MockRestServiceServer server;
    JevClient jevClient;

    @BeforeEach
    void setUp() {
        // 가짜 서버에 연결된 RestClient를 만들어 넣음. 재시도 대기 시간은 0으로 둬서 테스트가 바로 끝나게 함
        RestClient.Builder builder = RestClient.builder().baseUrl("https://jev.test");
        server = MockRestServiceServer.bindTo(builder).build();
        jevClient = new JevClient(builder.build(), "jev-1.14.0", "test-key", 2, 0);
    }

    @Test
    void 요청을_만들어_보내고_응답을_읽는다() {
        server.expect(requestTo(URL))
                .andExpect(method(HttpMethod.POST))
                .andExpect(header("TypeSafe-Danger-Zone-Images", "true"))
                .andExpect(jsonPath("$.model").value("jev-1.14.0"))
                .andExpect(jsonPath("$.state.photo").value("image-photo"))
                .andExpect(jsonPath("$.assets['image-photo'].format").value("jpg"))
                .andExpect(jsonPath("$.assets['image-photo'].data_base64").value(Base64.getEncoder().encodeToString(IMAGE)))
                .andExpect(jsonPath("$.questions.person.type").value("noul"))
                .andRespond(withSuccess(OK_BODY, MediaType.APPLICATION_JSON));

        JevResult result = jevClient.askYesNo(IMAGE, "jpg", QUESTIONS);

        assertThat(result.response().answers().get("person").noul()).isEqualTo(0.9);
        assertThat(result.response().usage().inputTokens()).isEqualTo(2803);
        assertThat(result.attempts()).hasSize(1);
        // 로그용 요청 원문에는 이미지 대신 크기만 들어감
        assertThat(result.requestBody()).contains("(생략: 3 bytes)").contains("person");
        server.verify();
    }

    @Test
    void 시간_초과는_재시도해서_성공한다() {
        // 연결하다가 시간 초과
        server.expect(requestTo(URL)).andRespond(withException(new SocketTimeoutException("Connect timed out")));
        // 응답은 왔는데 본문을 읽다가 시간 초과 (실제 서버에서 확인한 경우)
        server.expect(requestTo(URL)).andRespond(request -> new MockClientHttpResponse(new InputStream() {
            @Override
            public int read() throws SocketTimeoutException {
                throw new SocketTimeoutException("Read timed out");
            }
        }, HttpStatus.OK));
        server.expect(requestTo(URL)).andRespond(withSuccess(OK_BODY, MediaType.APPLICATION_JSON));

        JevResult result = jevClient.askYesNo(IMAGE, "jpg", QUESTIONS);

        // 시간 초과는 응답이 없어서 상태 코드 대신 이유가 남음
        List<JevCallAttempt> attempts = result.attempts();
        assertThat(attempts).hasSize(3);
        assertThat(attempts.get(0).statusCode()).isNull();
        assertThat(attempts.get(0).error()).contains("Connect timed out");
        assertThat(attempts.get(1).statusCode()).isNull();
        assertThat(attempts.get(1).error()).contains("Read timed out");
        assertThat(attempts.get(2).statusCode()).isEqualTo(200);
        server.verify();
    }

    @Test
    void 재시도를_다_해도_실패하면_예외에_시도_기록을_담는다() {
        // 첫 시도 + 재시도 2번 = 3번. 한도 초과(429)와 과부하(529)는 재시도 대상임
        server.expect(requestTo(URL)).andRespond(withTooManyRequests());
        server.expect(requestTo(URL)).andRespond(withStatus(HttpStatusCode.valueOf(529)));
        server.expect(requestTo(URL)).andRespond(withStatus(HttpStatusCode.valueOf(529)));

        JevCallException e = assertThrows(JevCallException.class,
                () -> jevClient.askYesNo(IMAGE, "jpg", QUESTIONS));

        assertThat(e.getAttempts()).extracting(JevCallAttempt::statusCode).containsExactly(429, 529, 529);
        server.verify();
    }

    @Test
    void 잘못된_요청은_재시도하지_않는다() {
        server.expect(requestTo(URL)).andRespond(withBadRequest().body("{\"error\": \"invalid question\"}"));

        JevCallException e = assertThrows(JevCallException.class,
                () -> jevClient.askYesNo(IMAGE, "jpg", QUESTIONS));

        assertThat(e.getAttempts()).hasSize(1);
        assertThat(e.getAttempts().get(0).statusCode()).isEqualTo(400);
        assertThat(e.getAttempts().get(0).responseBody()).contains("invalid question");
        server.verify();
    }

    // ===== ★ 추가 (가이드 06) 시작 =====
    @Test
    void 연결이_끝까지_안_되면_시도_기록을_담아_예외를_던진다() {
        // 첫 시도 + 재시도 2번 모두 연결 거부 (Jev 서버가 꺼져 있거나 네트워크가 끊긴 경우)
        for (int i = 0; i < 3; i++) {
            server.expect(requestTo(URL)).andRespond(withException(new ConnectException("Connection refused")));
        }

        JevCallException e = assertThrows(JevCallException.class,
                () -> jevClient.askYesNo(IMAGE, "jpg", QUESTIONS));

        assertThat(e.getMessage()).contains("연결 실패");
        assertThat(e.getAttempts()).hasSize(3);
        assertThat(e.getAttempts()).extracting(JevCallAttempt::statusCode).containsOnlyNulls();
        assertThat(e.getAttempts().get(2).error()).contains("Connection refused");
        server.verify();
    }
    // ===== ★ 추가 (가이드 06) 끝 =====

    // ===== ★ 추가 (가이드 06) 시작 =====
    @Test
    void API_키가_비어_있으면_요청을_보내지_않는다() {
        RestClient.Builder builder = RestClient.builder().baseUrl("https://jev.test");
        MockRestServiceServer emptyServer = MockRestServiceServer.bindTo(builder).build();
        JevClient noKeyClient = new JevClient(builder.build(), "jev-1.14.0", " ", 2, 0);

        IllegalStateException e = assertThrows(IllegalStateException.class,
                () -> noKeyClient.askYesNo(IMAGE, "jpg", QUESTIONS));

        assertThat(e.getMessage()).contains("JEV_API_KEY");
        // 기대한 요청을 하나도 등록하지 않았으므로, 요청이 한 번이라도 갔다면 여기서 실패함
        emptyServer.verify();
    }
    // ===== ★ 추가 (가이드 06) 끝 =====
}
```

**새로 친 부분**
- `import java.net.ConnectException;` 추가
- `연결이_끝까지_안_되면_시도_기록을_담아_예외를_던진다`
  - 가짜 서버에 "연결 거부" 3번을 등록함 (첫 시도 + 재시도 2번). `withException()`에 넣은 `IOException` 종류는 `RestClient`가 `ResourceAccessException`으로 바꿔 던짐 → `JevClient`의 `catch (ResourceAccessException e)`로 들어감
  - 3번째에서 `attempt > maxRetries`가 참이 되어 `"Jev 연결 실패"` 예외. 기존 테스트의 실패는 모두 **상태 코드가 있는 실패**(429·529·400)였고, 이 줄은 **응답 자체가 없는 실패**라 처음 실행됨
  - 응답이 없으므로 시도 기록의 상태 코드는 전부 `null`이고 이유(`error`)에 메시지가 남음 (`containsOnlyNulls()`)
- `API_키가_비어_있으면_요청을_보내지_않는다`: 1-4 참고. 키 자리에 `" "`를 넣어 `isBlank()`가 참이 되게 함

### 4-2. 남겨 둔 빈 곳 (보강 후)
| 클래스 | 남은 줄·분기 | 이유 |
|---|---|---|
| `VideoService` | 분기 1개 (이름 `null`) | 1-2. 테스트로도 실제 요청으로도 `null`이 오지 않음 |
| `FrameExtractor` | `catch (IOException)` 2줄, `InterruptedException` 3줄, 분기 1개 | 디스크 오류·스레드 중단. 분기는 `scores.txt`에 모르는 줄이 섞인 경우로 FFmpeg가 만들지 않음 |
| `JevClient` | `InterruptedException` 3줄, 분기 1개 (`status == 408`) | 408은 429·5xx와 같은 줄에서 재시도로 처리됨. 필요하면 2단계에서 추가 |
| `JudgmentService`, `FrameService`, `VideoFileStorage` | `catch (IOException)` 각 2줄 | 디스크 오류 |
| `VideoFrame`, `FrameJudgment` | getter 1줄씩 (`getVideo()`, `getId()`) | 기능 코드 어디에서도 아직 부르지 않음. 테스트를 쓸 일이 아니라 2단계에서 쓰게 되면 자연히 채워짐 |
| `MujinjigiApplication` | `main()` 2줄 | 테스트는 `main`을 거치지 않음 |

## 5. 알려진 한계 (면접에서 물어볼 만한 부분)
1. **분기 100%가 아님**: `null` 파일 이름처럼 도달할 수 없는 분기도 있음. 이런 분기는 테스트를 억지로 만들기보다 "왜 못 닿는지"를 설명할 수 있으면 됨. 판정 로직(2단계)만 100%를 목표로 둠 (handoff 8장)
2. **FFmpeg 실패 테스트는 PC에 FFmpeg가 있어야 돎**: 기존 추출 테스트와 같음. CI 서버를 만들면 FFmpeg 설치가 필요함
3. **커버리지는 실행 여부만 셈**: 예를 들어 영상 조회 테스트에서 `sizeBytes` 확인을 빼도 커버리지는 똑같이 6 / 6임. 줄을 채운 것보다 **무엇을 확인했는지(assert)**가 테스트의 가치임
4. **`catch` 줄은 여전히 테스트가 없음**: 파일 저장·삭제를 인터페이스 뒤로 빼면 가짜 구현으로 `IOException`을 낼 수 있지만, 지금은 클래스가 늘어나는 비용이 더 큼

## 스스로 답해볼 질문
1. 커버리지 % 목표를 두지 않고 빈 곳을 하나씩 판단한 이유는 무엇인가. 커버리지 100%면 버그가 없다고 할 수 있는가 (면접 질문)
2. 줄 커버리지와 분기 커버리지의 차이는 무엇인가. `a || b` 조건의 분기는 왜 4개로 세는가
3. 실패 경우 테스트에서 예외 종류만 확인하지 않고 메시지·시도 기록까지 확인하는 이유는 무엇인가
4. "요청을 보내지 않았다"는 어떻게 테스트로 확인했는가
5. `catch (IOException)` 줄을 테스트하려면 코드 구조를 어떻게 바꿔야 하는가. 이번에 바꾸지 않은 이유는 무엇인가
