## 1. 프로젝트 개요

무인매장 점주가 하루치 CCTV 녹화본과 키오스크 결제 내역을 올리면, Jev가 손님 행동을 판단하고 결제 내역과 대조해 미결제 의심 장면을 캡처와 함께 목록으로 보여주는 서비스임.

**만든 이유**
- 무인매장 점주는 재고와 매출이 안 맞을 때 녹화본을 직접 돌려보며 미결제 장면을 찾음
- 이 과정을 자동화해서 "확인할 장면만 골라주는" 도구를 만들고자 함

**목표**
- 백엔드 중심 포트폴리오로, 처음부터 끝까지 동작하는 서비스 완성
- 직접 만든 테스트 영상 기준으로 **미결제 놓침 0건**, **오탐률 개선 폭**을 숫자로 제시
- 설계 이유와 개선 과정을 기록해 면접에서 설명할 수 있게 함

**범위**
- 포함: 녹화본 업로드, 프레임 추출, Jev 이미지 판단, 결제 CSV 대조, 의심 장면 저장, 로그인, 웹 관리 화면, 모바일 앱(알림·확인), 웹·앱 연동
- 제외: 실시간 CCTV 연결, 실제 키오스크 연동, 결제 기능

## 3. 시스템 구조

```
[웹 (React)]  ──┐                      ┌──> [Jev 1.14]  프레임 판단
업로드·분석·관리 │                      │
                ├──> [Spring 서버] ─────┼──> [PostgreSQL · 파일 저장소]
[모바일 앱]   ──┘   공용 REST API       │     결과·캡처·확인 상태
알림·확인    <──── [FCM] <──────────────┘
             의심 장면 알림
```

**처리 흐름**
1. 웹에서 녹화본과 결제 CSV 업로드
2. 서버가 분석 작업(Job)을 등록하고 비동기로 처리
3. FFmpeg로 장면 변화가 큰 프레임만 추출
4. 프레임과 질문을 Jev에 보내 판단 결과와 확률을 받음
   - 행동 판단: 프레임마다 사람·집음·넣음·결제 질문
   - 진열대 전후 비교: 손님이 들어오기 전과 나간 뒤 진열대 사진으로 "상품이 사라졌나" 질문 (결정 001)
5. 진열대에서 사라진 상품과 결제 내역을 시간 기준으로 대조, 개수 비교는 Java 코드에서 함. 행동 판단은 의심도를 높이는 증거와 캡처 장면으로 씀
6. 의심도가 기준 이상이면 의심 장면으로 저장하고 FCM으로 앱에 알림
7. 점주가 웹이나 앱에서 "도난 맞음 / 아님" 확인 처리

**웹·앱 연동 원칙**

| 원칙 | 내용 |
|---|---|
| 하나의 API | 웹과 앱이 같은 API를 호출, 명세는 Swagger 하나로 관리 |
| 하나의 계정 | JWT 로그인으로 같은 계정을 웹과 앱에서 사용 |
| 하나의 상태 | 확인 처리 결과는 DB에만 저장, 화면은 열 때마다 API로 다시 조회 |
| 역할 분담 | 웹 = 영상·CSV 업로드, 분석 결과, 정확도 통계 / 앱 = 알림, 목록, 캡처 확인, 확인 처리 |
| 알림 | 의심 장면 저장 시 FCM으로 앱에 푸시, 웹은 목록에 새 항목 표시 |

기간은 정하지 않음. 각 단계의 완료 기준을 통과해야 다음 단계로 넘어감. **최소 완성선은 2단계**임.

### 0단계 · 첫 세팅과 검증
가장 불확실한 Jev 이미지 판단이 쓸 만한지부터 확인함.
- [x] 12장 "첫 세팅 순서" 완료 (Claude 기여자 차단 먼저)
- [x] Spring Boot 프로젝트 생성, 폴더 구조 세팅
- [x] Docker로 PostgreSQL 띄우기 (PC 포트 5433, PC에 설치된 PostgreSQL이 5432를 사용 중)
- [x] Jev 1.14 이미지 요청을 HTTP로 직접 보내보기 (사진 1장 + 질문 1개) → `JevClientLiveTest`, 400x400 이미지 1장 + 질문 2개에 입력 758토큰, 881ms
- [x] Jev 공식 문서에서 Java SDK 유무, 이미지 크기 제한, 요청 한도 확인 (6장에 정리)
- [x] 미결제 상황 사진 몇 장으로 "상품을 가방에 넣었나" 질문 테스트
  - 1차(무료 사진 8장): 30개 판단 중 29개 일치 → `docs/test-data/2026-10-28_jev_사진_테스트.md`
  - 2차(AI 생성 영상 8편, 프레임 109장): v0 기준 약 95% 일치. 자기 물건 오탐은 질문 v2로 줄였고, 도난 판정은 진열대 전후 비교가 행동 판단보다 정확함 → `docs/test-data/2026-10-29_jev_영상_테스트.md`, 결정 002

**완료 기준**: 사진 몇 장에 대한 Jev 판단이 실제와 대체로 맞음. 안 맞으면 질문을 더 잘게 쪼개 재시도함.

> **진행 메모 (2026-10-28)**: 0단계 마지막 항목(미결제 상황 판단)은 영상을 만들 수 있을 때마다 조금씩 2차 테스트로 이어감. 그동안 1단계 중 Jev 결과와 상관없이 필요한 항목(영상 업로드 API → 프레임 추출 → 측정 로그 → Jev 호출 서비스)부터 착수함. 질문 세트는 2차 테스트 결과를 보고 확정함.
>
> **0단계 완료 (2026-10-29)**: 1단계 질문 세트는 v2(`QuestionSetV2`)로 시작함. 넣은 곳 질문(v3)은 장바구니 장면이 생기면 다시 시험함. 남은 검증(사람이 진열대를 가리는 경우의 after 프레임 고르기, 실제 촬영 영상)은 2·3단계에서 필요할 때 진행함.

### 1단계 · 핵심 파이프라인
- [x] 영상 업로드 API (2026-10-28, 가이드 01)
- [ ] FFmpeg로 장면 변화가 큰 프레임만 추출해 저장
- [ ] Jev 호출 서비스: 프레임 + 질문 → 결과와 확률 저장
- [ ] 질문 세트 정의: 사람인가 / 상품을 집었나 / 가방·주머니에 넣었나 / 계산대로 갔나
- [ ] 호출 실패 시 재시도, 요청·응답·모델 버전 로그 저장
- [ ] 측정 로그 기록 시작 (8장 "측정 로그")

**완료 기준**: 테스트 영상 1개를 업로드하면 시각별 판단 결과가 DB에 쌓이고 조회 API로 확인됨.

### 2단계 · 결제 대조와 의심 판정 (최소 완성선)
- [ ] 결제 CSV 업로드와 저장
- [ ] 진열대 전후 비교: 손님이 들어오기 전·나간 뒤 프레임을 골라 진열대 칸별로 "사라졌나" 판단 (결정 001)
- [ ] 시각 맞추기: CCTV 시계와 키오스크 시계는 실제로 몇 초~몇 분씩 어긋남. 영상 시각 보정값과 대조 허용 범위(앞뒤 N초)를 설정 파일로 분리함
- [ ] 대조 로직: 상품을 집은 시각 전후 허용 범위 안에 결제가 있는지
- [ ] 개수 비교: 집은 개수와 결제된 개수 (Java 코드에서 계산)
- [ ] 금액·수량은 `long`(원 단위)으로 저장하고 계산함. `double`은 쓰지 않음 (원화는 소수점이 없고, `double`은 0.1 같은 값을 정확히 표현하지 못해 합계·비교에서 오차가 생김)
- [ ] 의심도 계산: Jev 확률 + 대조 결과, 기준값은 설정 파일로 분리
- [ ] 판정 로직(시각 맞추기, 대조, 개수 비교, 의심도 계산)은 Jev·DB 없이 동작하는 순수 Java 클래스로 분리함. 서비스에서 가장 책임이 큰 코드라 단위 테스트로 경계값(허용 범위 끝, 개수 같음·1개 차이, 기준값 바로 위·아래)을 모두 확인함
- [ ] 기준 이상이면 해당 프레임을 의심 장면으로 저장
- [ ] 긴 영상 처리를 작업(Job)으로 등록하고 진행 상태 조회 (비동기)

**완료 기준**: 영상과 CSV를 넣으면 미결제 영상은 의심 장면이 나오고, 정상 결제 영상은 대부분 걸러짐. 판정 로직 단위 테스트가 모두 통과함.

## 6. Jev 사용 메모

2026-10-28 공식 문서(https://docs.typesafe.ai)로 다시 확인한 내용임.

**호출 방식**
- `POST https://api.typesafe.ai/v1/systemone`, 인증은 `Authorization: Bearer <키>`
- 요청 본문: `model`, `state`(질문이 참고할 내용), `questions`(이름 → 질문), `assets`(이미지)
- 응답: `model`(실제 답한 모델 이름), `answers`(질문 이름별 답), `usage.input_tokens`(과금 대상)
- 공식 SDK는 Python, JavaScript만 있음. Java는 HTTP로 직접 호출함 (문서에 "어떤 언어에서든 HTTP API 직접 호출 가능"이라고 되어 있음)

**이미지 입력** (실험 기능, 공식적으로 운영 환경 사용 비권장)
- 이미지가 들어간 요청에는 `TypeSafe-Danger-Zone-Images: true` 헤더 필요
- 이미지는 `assets`에 한 번 등록하고, 그 참조 문자열을 `state`·`instructions`·`criteria` 안에 적어 연결함. 참조되지 않은 이미지가 있으면 400
- 전송 방식: multipart(권장) 또는 base64(`data_base64` + `format`). ~~URL이 아니라 base64로만~~ → 두 방식 모두 가능
- ~~1.14에서만 가능~~ → 이미지는 1.13, 1.14 모두 가능. Box 질문만 1.14 전용
- 제한: PNG/JPEG, 장당 16MiB, 가로·세로 각각 280~1,568px, 요청 전체 32MiB. **범위를 벗어나면 자동 축소 없이 거부되고, 한 장이라도 거부되면 요청 전체가 실패함** → 프레임 추출 시 긴 변을 1,568px 이하로 맞춰야 함
- EXIF 회전 정보는 적용하지 않음. 이미지를 똑바로 돌린 뒤 보냄
- 여러 질문이 같은 이미지를 쓰면 `state`에 한 번만 넣음 (`instructions`에 넣으면 질문마다 이미지 토큰이 다시 계산됨)

**질문 유형**
- Noul(예/아니오 확률), Choice(선택지 1~255개 중 하나), Score(0부터 시작하는 단계 1~10개), Box(이미지 속 위치, 1.14 전용)

**모델·가격·한도**
- 모델: `jev-1.14.0`(2026-10-14 출시), `jev-1.13.0`. 별칭 `jev-latest`, `jev-preview`는 현재 1.14.0을 가리킴
- 별칭은 새 버전이 나오면 바뀌므로 `jev-1.14.0`으로 고정하고, 응답의 `model` 값을 로그에 남김
- 문맥 길이: 요청당 64k, 질문당 32k 토큰 (`TypeSafe-Danger-Zone-Long-Context: true` 헤더로 262k까지)
- 가격: 입력 100만 토큰당 0.042달러, 출력 무료. 이미지도 입력 토큰으로 계산됨 (이미지 토큰 계산식은 아직 미공개)
- 요청 한도(rate limit) 수치는 공개되지 않음. 429(한도 초과), 529(서버 과부하)는 지수 백오프로 재시도함
- 실제 확인: 키가 없거나 비어 있으면 문서의 401이 아니라 **403**(`authentication_error`, "Must supply an API key!")이 옴 (2026-10-28)

**사용 원칙**
- TypeSafe 공식 권고: 이미지 판단은 텍스트보다 성능이 낮음, 복잡한 질문은 단순한 질문 여러 개로 쪼갤 것
- 산술·개수 세기는 Jev의 공식 약점임. 개수 비교와 계산은 반드시 Java 코드에서 함

## 7. 정확도 목표와 측정

**정답표**: 테스트 영상마다 "몇 분 몇 초에 무슨 일이 있었나"와 결제 여부를 기록한 표. `docs/test-data/`에 보관함.

**지표 정의** (이벤트·놓침·오탐의 정확한 뜻은 14장)
- **놓침 건수**: 정답표상 미결제인데 의심 장면으로 잡지 못한 건수. **목표 0건**
- **오탐률**: 정답표상 정상 결제인 이벤트 중 의심 장면으로 잘못 분류된 비율
- 오탐률은 목표치를 정하지 않고, 개선 전후 수치로 제시함 (예: 40% → 15%)

**측정 원칙**
- 같은 테스트 영상 묶음, 같은 설정으로 측정함
- 질문 문구, 의심도 기준값 등을 바꿀 때마다 재측정하고 전후를 기록함
- **정답표는 Jev를 호출하기 전에 작성함.** 결과를 본 뒤 정답을 정하면 결과에 끌려 정확도가 실제보다 좋게 나옴 (2일차에 한 번 어겼고, 그 측정은 한계로 표시함)

테스트 영상 촬영 계획은 완성도를 보고 추후 결정함.

### 테스트 환경과 운영 환경의 차이
지금 테스트 영상에서 통과해도 실제 매장 녹화본에서 그대로 동작한다는 보장은 없음. 차이를 미리 적어 두고, 3단계 실제 녹화본 측정과 README "한계"에 그대로 씀.

| 항목 | 지금 테스트 영상 | 실제 매장 (가정) | 영향 |
|---|---|---|---|
| 영상 길이 | 장면 하나 4~20초 | 하루 24시간 녹화 | 빈 매장 시간이 대부분 → 프레임 고르기 효과가 커짐. 긴 영상 처리 시간·실패 처리 필요 |
| 화질·조명 | AI 생성, 밝은 주간 | 압축 노이즈, 야간 적외선(흑백) | scene 점수 기준 0.005가 노이즈에 묻힐 수 있음 (결정 003 한계) |
| 손님 수 | 한 명 | 여러 명이 동시에, 연달아 | 진열대 전후 비교용 빈 화면이 없을 수 있음. 누가 가져갔는지 구분 어려움 (결정 001 단점) |
| 시계 | 영상 하나 안에서만 봄 | CCTV와 키오스크 시계가 어긋남 | 대조 허용 범위가 좁으면 정상 결제도 의심으로 잡힘 (5장 2단계 "시각 맞추기") |
| 카메라 | 영상마다 구도가 다름 | 매장마다 고정 | 진열대 칸 위치를 매장별로 한 번만 설정하면 됨 |

### 운영 비용 추정
Jev 비용은 "프레임 수 × 프레임당 토큰"으로 정해짐. 매장 하나 기준 하루 비용을 아래 가정으로 추정함. 가정 값은 실제 녹화본을 받으면 고침.

| 항목 | 값 | 근거 |
|---|---|---|
| 카메라 수 | 1대 | 가정 |
| 하루 중 손님이 있는 시간 | 4시간 | 가정 (나머지는 빈 매장이라 프레임 고르기에서 빠짐, 결정 003) |
| 프레임 간격 | 1초에 1장 | 현재 설정 |
| Jev로 보내는 프레임 | 14,400장 | 4시간 × 3,600초 |
| 프레임당 입력 토큰 | 약 2,800 | 1280x720, 질문 4개 실측 2,803 (결정 002) |
| 하루 입력 토큰 | 약 4,000만 | 14,400 × 2,803 |
| 하루 비용 | 약 1.7달러 | 100만 토큰당 0.042달러 (6장) |
| 한 달 비용 | 약 51달러 | 30일 |

- 진열대 전후 비교 요청(방문당 1회, 칸만 잘라 약 1,500토큰)은 프레임 판단보다 훨씬 적어서 위 표에서 뺌
- 이 표는 "프레임 간격·이미지 크기·보내는 프레임 수를 줄이는 개선"이 얼마짜리인지 설명하는 기준선임. 개선할 때마다 같은 표로 다시 계산해 전후를 기록함

## 8. 포트폴리오 기록 체계

### 원칙
**바꾸기 전에 먼저 재고, 바꾼 뒤 같은 조건으로 다시 잼.**
다 만든 뒤 기록하려 하면 개선 전 상태를 다시 만들 수 없음. 작업 중에 바로 기록함.

### 기록 대상
- 숫자로 전후 비교가 되는 개선 (시간, 비용, 정확도, 호출 수, 토큰 사용량)
- 원인이 바로 보이지 않아 추적 과정이 있었던 문제
- 대안이 여러 개였고 이유를 갖고 하나를 고른 설계 결정

**기록하지 않는 것**: 오타, 단순 설정 실수, 설치 오류 등 원인과 해결이 한 줄로 끝나는 것

### 예상 기록거리
- 프레임 필터링으로 Jev 호출 수·처리 시간 감소 (전체 프레임 vs 장면 변화 프레임)
- 질문 쪼개기·문구 수정으로 놓침 건수·오탐률 개선
- 비동기 작업 전환으로 업로드 응답 시간 단축
- 이미지 크기 조정으로 Jev 토큰 사용량 감소
- 데이터가 쌓였을 때 의심 장면 목록 조회 쿼리 개선

### 측정 로그
1단계부터 분석 작업마다 아래 값을 DB(또는 CSV)에 남김. 이후 그래프는 이 로그로 그림.
- 작업 ID, 영상 길이, 추출 프레임 수
- Jev 호출 수, 입력 토큰 수, 실패·재시도 수
- 단계별 처리 시간 (프레임 추출, Jev 판단, 대조)
- 사용한 설정값 (장면 감지 민감도, 의심도 기준값, 질문 세트 버전)

### 시각 자료와 캡처
- 직접 생성 가능한 것: 측정 로그 그래프(PNG), 웹 화면 캡처, 터미널 측정 결과(텍스트) → Claude Code가 생성해 저장
- 직접 볼 수 없는 화면: IDE 프로파일러, 휴대폰 앱, 클라우드 콘솔 등 → Claude Code가 사용자에게 캡처를 요청함
- 저장 위치: `docs/portfolio/assets/`
- 파일명: `YYYY-MM-DD_주제_before.png`, `YYYY-MM-DD_주제_after.png`

```markdown
- 면접 질문이나 정말 중요한 것만 5개 정도로 추림
- Claude Code는 질문만 씀. 답은 사용자가 자기 말로 직접 씀
```

## 11. 보안 규칙

- Jev API 키, DB 비밀번호, JWT 비밀키는 `.env`에만 둠. 저장소에는 `.env.example`(키 이름만)을 올림
- Claude Code가 `.env`를 읽지 못하도록 권한 설정함 (12장)
- 비밀번호는 BCrypt로 암호화해 저장함
- Jev 호출은 서버에서만 함. 웹·앱에 API 키를 넣지 않음
- 얼굴이 나오는 테스트 영상, 업로드 파일, 추출 프레임은 저장소에 올리지 않음
- 저장소는 포트폴리오 공개 전 커밋 기록에 비밀값이 없는지 한 번 더 점검함

## 12. 첫 세팅 순서 (첫 커밋 전에 반드시 완료)

Claude가 붙은 커밋이 한 번이라도 push되면 지우려면 기록을 다시 써야 함. 그래서 이 순서를 가장 먼저 함.

**1) Git 작성자를 본인 계정으로 설정**
```bash
git config user.name "본인 GitHub 이름"
git config user.email "본인 GitHub 이메일"
```

**2) Claude Code attribution 끄기**
- `.claude/settings.json`에 attribution 비활성화 설정을 넣음
- 버전마다 설정 형식이 달랐고(`includeCoAuthoredBy` → `attribution`), 설정이 무시된 버그 제보도 있었음
- 세팅 당일 Claude Code 공식 설정 문서 기준 형식으로 넣고, 아래 3)의 훅으로 이중 차단함

**3) commit-msg 훅으로 Claude 문구 자동 제거**
`scripts/git-hooks/commit-msg` 파일:
```sh
#!/bin/sh
# 커밋 메시지에서 Claude 기여자 문구 제거
sed -i.bak \
  -e '/[Cc]o-[Aa]uthored-[Bb]y:.*[Cc]laude/d' \
  -e '/[Cc]o-[Aa]uthored-[Bb]y:.*anthropic/d' \
  -e '/Generated with.*Claude Code/d' \
  "$1" && rm -f "$1.bak"
```
적용:
```bash
chmod +x scripts/git-hooks/commit-msg
git config core.hooksPath scripts/git-hooks
```
- 훅은 저장소에 함께 커밋해 두어 다른 PC에서도 같은 설정을 쓸 수 있게 함

**4) .env 읽기 차단**
- `.claude/settings.json`의 권한(permissions) 설정에 `.env` 파일 읽기 거부 규칙을 넣음 (`.env.example`은 허용)
- 정확한 문법은 세팅 당일 공식 문서로 확인함

**5) .gitignore 확인**
- `.env`, 영상·업로드·프레임 폴더, 빌드 결과물, IDE 설정 파일 제외

**6) 확인 테스트**
- 테스트 커밋을 하나 만들고 `git log -1`로 메시지에 Claude 문구가 없는지 확인 후 push함
- push 후 GitHub 저장소의 Contributors에 본인만 있는지 확인함

## 13. 미정 사항

- 테스트 영상 촬영 계획 (개수, 상황 구성): 1~2단계 완성도를 보고 결정
- 클라우드 서비스 종류: 4단계에서 결정
- **매장 상품과 손님 물건 구분** (2026-10-28 제기): 손님이 자기 휴대폰을 가방에 넣는 장면은 사진 한 장으로 보면 미결제 장면과 거의 같음
  - 프레임 하나만으로는 구분이 어려움. "진열대에서 집었는가"를 앞뒤 프레임으로 추적해야 할 가능성이 큼
  - 0단계 직접 촬영의 N4·N5 장면으로 먼저 확인하고, 1~2단계 설계 때 방법을 결정함

## 14. 용어 정의

문서·코드·커밋에서 아래 뜻으로만 씀. 새 용어가 생기거나 뜻이 바뀌면 여기부터 고침.

| 용어 | 뜻 | 비고 |
|---|---|---|
| 녹화본 | 점주가 올리는 CCTV 영상 파일 하나 | 코드에서는 `Video` |
| 프레임 | 녹화본에서 뽑은 정지 사진 한 장. 기본 1초에 1장 | |
| scene 점수 | FFmpeg가 계산한, 연속한 두 프레임이 얼마나 다른지 나타내는 0~1 값. 화면 전체 기준 | 결정 003 |
| 활동 구간 | scene 점수가 기준(0.005)을 넘은 프레임의 앞뒤 2초를 합친 구간. Jev로 보내는 프레임은 이 구간 안의 것뿐임 | 결정 003. 기준값·앞뒤 초는 설정 |
| 질문 세트 | 프레임 하나에 Jev로 함께 보내는 질문 묶음. 버전으로 구분함 (v0~v3) | 현재 v2 (`QuestionSetV2`) |
| 판정 기준 | Jev 확률을 예/아니오로 바꾸는 경계값. 현재 0.5 | 의심도 기준값과 다름 |
| 방문 | 손님 한 명(또는 함께 온 일행)이 들어와서 나갈 때까지 | 진열대 전후 비교와 정확도 측정의 단위 |
| 칸 | 진열대 사진에서 상품 한 종류가 놓인 영역. "사라졌나"를 묻는 단위 | 영어 문서·코드에서는 ROI |
| 진열대 전후 비교 | 방문 전(before)과 방문 후(after) 진열대 사진을 칸별로 비교해 "상품이 사라졌나"를 묻는 것 | 결정 001 |
| 의심도 | Jev 확률과 결제 대조 결과로 계산한, 방문이 미결제일 가능성을 나타내는 값 | 계산식은 2단계에서 정하고 결정 기록으로 남김 |
| 의심 장면 | 의심도가 기준값 이상이라 점주에게 보여주는 항목. 대표 캡처 프레임과 판정 근거(사라진 칸, 대조 결과)를 담음 | 방문 하나당 몇 개를 만들지는 2단계에서 정함 |
| 정답표 | 테스트 영상마다 실제로 일어난 일을 적은 표. Jev 호출 전에 작성함 (7장) | `docs/test-data/` |
| 프레임 정답 | 프레임 하나에 대한 질문별 정답 (예: 7초 프레임 putting_in_bag = 예) | 0단계처럼 Jev 질문의 정확도를 볼 때 씀 |
| 이벤트 | 정답표의 한 줄. 방문 하나와 그 결과(미결제 / 정상)를 뜻함. 정상에는 결제를 마친 방문과 아무것도 안 가져간 방문(N1, N4, N5 같은 경우)이 모두 들어감 | 서비스 정확도(놓침, 오탐률)를 볼 때 씀 |
| 놓침 | 미결제 이벤트인데 의심 장면이 하나도 나오지 않은 것 | 목표 0건 (7장) |
| 오탐 | 정상 이벤트인데 의심 장면이 나온 것. 오탐률 = 오탐 수 ÷ 정상 이벤트 수 | 개선 전후로 제시 (7장) |
