# [트러블슈팅] 판단 목록을 조회할 때 프레임 수만큼 쿼리가 더 나감 (N+1)

## 현상
- 판단 목록 조회 API(`GET /api/videos/{videoId}/judgments`)는 판단 결과(`FrameJudgment`)마다 그 프레임의 시각(`timeSec`)을 같이 돌려줌
- `FrameJudgment`는 프레임을 `@ManyToOne(fetch = LAZY)`로 가짐. 판단 결과만 먼저 읽고, 프레임은 실제로 꺼낼 때(`judgment.getFrame().getTimeSec()`) 읽음
- 가이드 03을 만들면서 판단 5개를 조회해 응답으로 바꾸는 과정을 Hibernate 통계로 셌음. **쿼리가 1번이 아니라 6번 나감**
- 영상 하나에서 고른 프레임 수만큼 쿼리가 늘어남. P1은 16장이라 17번이고, 1시간 영상이면 수백 번이 됨

## 원인 추적 과정
1. **조회 조건에 프레임이 들어가니 같이 읽어 올 것이라고 생각함**
   - 조회 조건이 `where j.frame.video.id = :videoId order by j.frame.timeSec`이라 SQL에 이미 `video_frames` 조인이 들어감
   - 실제 SQL을 켜서(`spring.jpa.show-sql=true`) 확인함. 첫 쿼리는 `frame_judgments join video_frames`가 맞았음
   - 하지만 `select` 절에는 `frame_judgments`의 칸만 있었음. **조인은 조건과 정렬에만 쓰이고, 프레임 값은 가져오지 않음**
2. **그 뒤에 나온 쿼리 5개를 확인함**
   - `select ... from video_frames where id=?`가 판단 결과 수만큼 반복됨
   - 응답 DTO로 바꾸면서 `getFrame().getTimeSec()`을 부를 때마다, 지연 로딩(LAZY)으로 프레임을 하나씩 읽은 것임
3. **즉시 로딩(EAGER)으로 바꾸면 해결될지 생각함**
   - EAGER도 JPQL 조회에서는 결과를 먼저 읽고 연관 객체를 따로 읽어서 N+1이 그대로 남음
   - 프레임이 필요 없는 조회(재판단 시 이미 한 프레임 id 확인 등)에서도 항상 읽게 됨. 그래서 엔티티 설정은 LAZY로 두고, 필요한 조회에서만 같이 읽기로 함

## 진짜 원인
- JPQL의 `join`(또는 `j.frame.video.id` 같은 경로 식)은 **SQL 조인만 만들고, 연관 엔티티를 채우지 않음**
- 프레임이 LAZY라서, 결과 N개를 읽은 뒤 프레임을 꺼낼 때마다 쿼리가 1번씩 더 나감 → 1 + N번

## 해결
- 레포지토리에 **fetch join** 쿼리를 둠. `join fetch`는 조인한 프레임의 칸까지 `select`에 넣어 한 번에 채움

```java
@Query("""
        select j from FrameJudgment j
        join fetch j.frame f
        where f.video.id = :videoId and j.questionSetVersion = :version
        order by f.timeSec
        """)
List<FrameJudgment> findAllWithFrame(Long videoId, String version);
```

| 항목 | Before (join만) | After (join fetch) |
|---|---|---|
| 판단 5개 조회 쿼리 수 | 6번 (1 + 5) | **1번** |
| P1(16장) 기준 | 17번 | 1번 |
| 늘어나는 방식 | 프레임 수에 비례 | 프레임 수와 상관없이 1번 |

- 측정 조건: 테스트 영상 업로드 → 프레임 5장 추출 → 판단 5개 저장 후, 영속성 컨텍스트를 비우고(`em.clear()`) 조회함. Hibernate `Statistics.getPrepareStatementCount()`로 셈
- 실제 서버에서 P1 판단 16개 조회 API 응답 시간: 0.03초

## 배운 점
- **`join`과 `join fetch`는 다름.** `join`은 SQL 조건용, `join fetch`는 연관 객체까지 채우는 용도임
- N+1은 테스트가 통과해도 드러나지 않음. 결과는 같고 쿼리 수만 다르기 때문임. **SQL 로그나 통계로 쿼리 수를 직접 세야** 보임
- 같은 트랜잭션 안에서 방금 저장한 프레임은 1차 캐시에 있어서 추가 쿼리가 안 나감. 측정할 때 `em.clear()`를 하지 않으면 N+1이 숨음
- 해결은 엔티티를 EAGER로 바꾸는 것이 아니라, LAZY를 기본으로 두고 필요한 조회에서만 fetch join을 쓰는 것임
