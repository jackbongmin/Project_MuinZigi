# [트러블슈팅] 가짜 서버 테스트는 통과했는데, 실제 시간 초과는 재시도되지 않고 500이 남

## 현상
- Jev 호출 재시도를 만듦. 시간 초과·연결 실패(`ResourceAccessException`)와 429·5xx 응답이 나면 최대 2번 다시 보냄
- 가짜 서버(`MockRestServiceServer`) 테스트는 모두 통과함. 시간 초과는 `withException(new SocketTimeoutException(...))`으로 흉내 냈음
- 실제 서버에서 확인하려고 응답 시간 제한을 1ms로 줄여(`--jev.read-timeout-ms=1`) 일부러 시간 초과를 냄
- 기대는 "3번 시도 → 502 + 시도 기록 3줄"이었음. 실제로는 **재시도 없이 1번 만에 500**이 나고, **시도 기록도 0줄**이었음

## 원인 추적 과정
1. **재시도 로직의 횟수 계산이 틀렸다고 의심함**
   - 횟수가 틀렸다면 2번이나 4번 시도했어야 함. 그런데 기록이 아예 0줄이었음
   - 시도 기록은 `catch (ResourceAccessException e)` 안에서 남김. 0줄이라는 것은 **이 catch에 아예 들어오지 않았다**는 뜻으로 봄
2. **서버 로그에서 실제 예외 종류를 확인함**
   - 로그: `RestClientException: Error while extracting response for type [java.lang.String] and content type [application/octet-stream]`, 맨 아래 원인은 `SocketTimeoutException: Read timed out`
   - 시간 초과는 맞았지만, 예외 종류가 `ResourceAccessException`이 아니라 그 부모인 `RestClientException`이었음
3. **왜 종류가 다른지 확인함**
   - 시간 초과가 나는 시점이 두 가지임
     - 요청을 보내거나 응답 헤더를 기다리다가 나면 → `ResourceAccessException`
     - 헤더는 받았고 **본문을 읽다가** 나면 → 본문 변환 단계(`toEntity(String.class)`)의 오류라서 `RestClientException`
   - 가짜 서버의 `withException`은 첫 번째 경우만 흉내 냄. 그래서 테스트가 통과했음
4. **테스트로 재현함**
   - 가짜 응답의 본문(`InputStream`)이 읽을 때 `SocketTimeoutException`을 던지게 만듦
   - 실제 서버와 **같은 메시지**(`Error while extracting response ...`)로 테스트가 실패하는 것을 확인함. 원인이 맞다는 근거로 봄

## 진짜 원인
- `retrieve().onStatus(...).toEntity(String.class)`로 응답을 받으면, 본문을 읽다 난 입출력 오류는 `RestClientException`으로 감싸짐
- 재시도 코드는 `ResourceAccessException`만 잡고 있어서, 본문 읽기 중 시간 초과는 그대로 위로 던져져 500이 됨. 기록을 남기는 코드도 건너뜀

## 해결
- 응답을 `exchange()`로 직접 읽도록 바꿈. `exchange` 안에서 난 입출력 오류는 연결 실패와 똑같이 `ResourceAccessException`으로 감싸짐
  - `exchange`는 4xx·5xx에도 예외를 던지지 않음. 그래서 "모든 상태를 예외 없이 받기" 위해 쓰던 `onStatus(status -> true, ...)` 꼼수도 없앰

```java
// 전: 본문을 읽다 난 시간 초과가 RestClientException이 되어 catch에 안 걸림
.retrieve()
.onStatus(status -> true, (request, res) -> { })
.toEntity(String.class);

// 후: 본문 읽기까지 exchange 안에서 함 → 입출력 오류는 모두 ResourceAccessException
.exchange((request, res) -> ResponseEntity.status(res.getStatusCode())
        .body(new String(res.getBody().readAllBytes(), StandardCharsets.UTF_8)));
```

- 본문 읽기 시간 초과를 재현한 테스트를 `JevClientTest.시간_초과는_재시도해서_성공한다()`에 남김 (연결 시간 초과 → 본문 읽기 시간 초과 → 성공)
- 결과: 실제 서버에서 3번 시도 후 502, 시도 기록 3줄. 같은 요청을 원래 설정으로 다시 부르면 실패한 프레임부터 이어서 16개 모두 판단함

| 항목 | 고치기 전 | 고친 후 |
|---|---|---|
| 본문 읽기 시간 초과 시 시도 횟수 | 1번 | 3번 (첫 시도 + 재시도 2번) |
| 응답 상태 | 500 | 502 |
| 남은 시도 기록 | 0줄 | 3줄 |

## 배운 점
- **가짜 서버는 내가 상상한 실패만 흉내 냄.** 같은 "시간 초과"도 어느 단계에서 나느냐에 따라 예외 종류가 다름. 실제 서버에서 일부러 실패를 만들어 보는 확인이 필요함
- 기록이 "틀린 값"이 아니라 "0줄"이었던 것이 단서였음. 로직이 틀린 게 아니라 **그 코드에 아예 들어가지 않았다**는 뜻임
- 재현 테스트를 먼저 실패시키고(같은 메시지 확인) 고친 뒤 통과시키면, 원인을 맞게 짚었는지 확인할 수 있음
- 응답 시간 제한을 1ms로 줄이는 것처럼, **설정값만 바꿔서 장애를 만드는 방법**은 코드를 고치지 않고 실제 환경의 실패를 확인할 수 있음
