# [결정] Jev 재시도는 반복문으로 직접 만들고, 시도마다 요청·응답 원문을 DB에 기록함

## 상황
- Jev는 요청 한도(rate limit) 수치를 공개하지 않음. 429(한도 초과), 529(과부하)가 오면 지수 백오프로 다시 보내라고 안내함
- 지금은 프레임 하나라도 실패하면 판단 요청 전체가 500으로 끝남. 다시 부르면 이어서 하지만, 사람이 다시 불러야 함
- 판단이 이상할 때 Jev가 실제로 무엇을 받고 무엇을 답했는지 볼 방법이 없음. 확률·모델·토큰만 저장하고 있음

## 선택지 1 · 재시도를 어떻게 만들까
| 방법 | 장점 | 단점 |
|---|---|---|
| A. Spring `@Retryable`(Spring Framework 7 기본 기능) | 어노테이션 한 줄. 설정이 짧음 | 시도마다 무슨 일이 있었는지(상태 코드, 원문, 걸린 시간) 꺼내려면 리스너를 따로 붙여야 함. 프록시로 동작해서 같은 클래스 안에서 부르면 적용이 안 됨 |
| B. Spring `RetryTemplate` | 코드로 정책을 정함. 테스트에서 대기 시간 조절 쉬움 | A와 같이 시도별 기록을 남기려면 리스너가 필요함 |
| **C. 반복문으로 직접 구현** | 시도마다 상태 코드·원문·시간을 바로 기록함. 어떤 상태를 재시도하는지 코드에 그대로 보임 | 코드가 30줄쯤 늘어남. 백오프·지터를 직접 계산함 |

## 선택지 2 · 원문을 어디에 남길까
| 방법 | 장점 | 단점 |
|---|---|---|
| A. 애플리케이션 로그 파일 | 코드가 가장 적음 | 프레임·영상과 연결해서 찾기 어려움. 측정 로그(8장)로 집계하려면 파일을 다시 읽어야 함 |
| **B. DB 테이블 (`jev_call_logs`, 시도마다 한 줄)** | 프레임과 연결돼 SQL로 바로 찾고 집계함 (재시도 비율, 평균 응답 시간) | 저장 공간을 씀. 오래된 기록을 지우는 정책이 필요함 |

## 결정
- **재시도는 C(직접 구현)**, **원문은 B(DB 테이블)**
- 재시도 기준은 Jev 공식 SDK 기본값을 따름
  - 대상: 408, 429, 5xx(529 포함), 연결 실패·시간 초과
  - 횟수: 최대 2번 재시도 (총 3번)
  - 대기: 0.5초부터 두 배씩, 최대 5초. 매번 최대 25%를 무작위로 줄임(지터)
- 400·401·403·422처럼 요청이 잘못된 경우는 다시 보내도 똑같이 실패하므로 재시도하지 않음
- 재시도까지 실패하면 502(Bad Gateway)를 돌려줌. 우리 서버가 아니라 외부 서버 문제라는 뜻임
- 요청 원문에서 이미지 base64는 크기만 남김. 프레임 한 장이 약 200KB인데, 이미지를 빼면 요청 원문은 약 800자임. 이미지는 디스크의 프레임 파일로 다시 볼 수 있음

## 이유
- 원문 기록이 이번 작업의 목적 중 하나라, 시도별 기록을 가장 쉽게 남기는 방법을 고름
- 재시도 비율과 응답 시간은 다음 항목(측정 로그)에서 바로 집계할 값임. DB에 있으면 SQL 한 줄로 셈
- 직접 만든 코드라서, 실제 서버 확인에서 본문 읽기 시간 초과가 재시도되지 않는 문제를 찾고 바로 고칠 수 있었음 (트러블슈팅 2026-10-30)

## 트레이드오프
- 기록 저장 공간: 시도 한 줄 약 1KB. 하루 14,400장 기준 약 15MB/일. 보관 기간을 정해 오래된 기록을 지우는 작업이 나중에 필요함
- 요청 원문은 재시도마다 같은 내용이 중복 저장됨. 재시도는 드물어서 그대로 둠
- 판단 요청이 실패하면 사람이 다시 불러야 하는 점은 그대로임. 2단계에서 작업(Job)으로 바꿀 때 자동으로 이어서 하게 함
