# [결정] Jev 판단 결과를 질문별 칸이 아니라 jsonb 한 칸에 저장함

## 상황
- 프레임 한 장을 Jev에 보내면 질문마다 "예"일 확률이 돌아옴 (`{"person": 0.99, "holding_product": 0.10, ...}`)
- 질문 세트는 앞으로도 바뀔 예정임
  - 지금은 v2(질문 4개)로 시작하지만, v3(질문 7개)은 장바구니 장면이 생기면 다시 시험하기로 함 (handoff 5장 0단계 메모)
  - 질문 문구를 고칠 때마다 전후 정확도를 비교해야 함 (handoff 7장 측정 원칙). 그래서 버전이 다른 결과가 한 테이블에 같이 쌓임
- 읽을 때는 항상 "판단 하나 = 질문 전체"를 통째로 읽음. 질문 하나만 따로 읽는 경우는 없음

## 선택지
- **A: 질문마다 칸** (`person`, `holding_product`, `putting_in_bag`, `paying`)
  - 장점: 가장 단순함. Java 코드에서 `getPerson()`처럼 바로 꺼냄. SQL로 비교·집계하기 쉬움
  - 단점: 질문 세트가 바뀔 때마다 테이블을 고쳐야 함. v2와 v3이 같이 있으면 서로 안 쓰는 칸이 비어 있음
- **B: 자식 테이블** (`judgment_id, question, probability`를 한 줄씩)
  - 장점: 질문이 바뀌어도 테이블은 그대로임. 정규화된 구조
  - 단점: 판단 하나에 4~7줄이 생김. 읽을 때마다 조인이 필요하고, 목록 조회에서 N+1을 한 번 더 신경 써야 함
- **C: JSON 한 칸** (PostgreSQL `jsonb`, Java에서는 `Map<String, Double>`)
  - 장점: 질문이 바뀌어도 테이블은 그대로임. 판단 하나를 한 줄로 읽음. `answers->>'person'`처럼 SQL로도 꺼낼 수 있음
  - 단점: PostgreSQL 전용 기능이라 DB를 바꾸기 어려움. 질문 이름을 잘못 쓰면(오타) 컴파일 때 못 잡음. 키 순서를 지키지 않음

## 결정과 이유
- **C를 선택함**
- 질문 세트를 바꾸는 것이 이 프로젝트의 핵심 실험 방법이라, 그때마다 테이블을 고치는 A는 맞지 않음
- 읽는 단위가 항상 "판단 하나 통째"라서 B처럼 한 줄씩 나눌 이유가 없음
- DB를 PostgreSQL로 고른 이유 중 하나가 JSON 저장·검색이었음 (handoff 2장). 다른 DB로 옮길 계획은 없음
- 어떤 질문으로 나온 결과인지는 `questionSetVersion` 칸으로 구분함
- 질문 이름 오타 위험은 이름을 `FrameQuestions` 한 곳에서만 정의하는 것으로 줄임

## 확인 (2026-10-30)
- Hibernate `@JdbcTypeCode(SqlTypes.JSON)`로 `Map<String, Double>`이 `jsonb`로 저장되고 다시 읽힘
- P1 영상 16장을 실제 Jev로 판단해 저장·조회함 (가이드 03 4-2)

## 다시 볼 조건
